# 참고 자료 분석

- 날짜: 2026-11-27
- 확인 방법: 아래 네 자료는 원문(블로그 글, 명세, 저장소 문서)을 직접 읽었다. 영상 두 편은 시청하지 못했고 게시자가 쓴 설명문이나 제목만 참고했다.

각 자료에서 가져올 것, 가져오지 않을 것, 그리고 gotgan 계획에 주는 영향을 정리한다.

## 1. LangChain, "How to build a knowledge factory" (2026-11-21)

출처: https://www.langchain.com/blog/knowledge-factory (Harrison Chase)

### 내용

- **컨텍스트와 지식의 구분**: 컨텍스트는 에이전트가 작업할 때 가진 것이고, 지식은 작업을 올바르게 하도록 유지하는 재사용 가능한 이해다. 지식은 컨텍스트의 일부일 뿐 전부가 아니다.
- **지식의 세 종류**: 일하는 방법(스킬), 업무가 돌아가는 방식(도메인 지식), 최신 정보를 얻는 곳(데이터 접근 안내). 정본이 이미 다른 곳에 완전하게 있으면 사본을 유지하지 말고, 어디에 무엇이 있고 어떻게 조회하는지만 유지하라고 한다.
- **팩토리의 세 부품**
  1. 신고: 작업하는 에이전트가 없는 지식이나 틀린 지식을 신고하는 도구. 올바른 수정안을 함께 제안할 수 있다.
  2. 큐레이터 에이전트: 주기적으로 백그라운드에서 돌며 지식을 갱신한다. 입력은 원천 자료, 에이전트 실행 기록, 신고다.
  3. 저장소: 가장 덜 중요하다고 한다. 표준이 아직 없으니 형식을 지나치게 규정하지 말라고 한다.
- **작업 에이전트가 지식을 직접 고치면 안 되는 이유**: 자기 목표를 달성하려는 에이전트에게 유지 관리를 맡기면 지식이 어지럽고 모순으로 가득해진다.
- **시작 방법**: 모든 것을 미리 문서화하지 않는다. 반복되는 업무 하나에서 시작해 에이전트가 막히는 곳을 보고 그 고리를 닫는다.

### 글이 다루지 않는 것

큐레이터의 변경에 대한 검증과 사람의 승인, 문장 단위 근거, 접근 권한, 원본 개정에 따른 무효화, 효과를 보여 주는 측정값. 큐레이터가 지식을 직접 고친다.

### gotgan에 주는 영향

| 항목 | 판단 |
| - | - |
| 신고 기능 | **채택.** 현재 계획의 "수요 기반 큐레이션"을 구현하는 가장 단순한 방법이다. 질의 로그 분석보다 먼저 만든다 |
| 작업 에이전트와 큐레이터의 분리 | 이미 같은 방향이다. gotgan은 여기에 검증과 승인을 더한다 |
| 지식 유형 "자료 안내" | **채택.** 어느 원본이 현재 유효한지, 무엇이 어디에 있는지를 지식 유형에 추가한다. "현재 유효한 내용 식별"이라는 문제에 직접 대응한다 |
| 정본이 있으면 사본을 만들지 않는다 | 이미 같은 방향이다(선택적 큐레이션). 자주 바뀌는 수치는 지식으로 옮기지 않고 원본 위치를 가리킨다 |
| 반복 업무 하나에서 시작 | **채택.** 제품 정의에 첫 반복 업무를 정하는 항목을 추가한다 |
| 저장 형식을 과하게 규정하지 않는다 | **주의 사항으로 채택.** Vault 규격은 PoC에 필요한 최소한만 정한다 |
| 큐레이터가 승인 없이 직접 반영 | 채택하지 않는다. 다만 이것이 gotgan이 치르는 추가 비용이므로, 검증·승인이 그만한 값을 하는지가 실험의 질문이 된다 |

gotgan과 이 글의 차이는 **근거 추적, 검증·승인, 권한** 세 가지다. 이 세 가지가 필요 없는 상황이라면 글의 방식이 더 싸다.

## 2. Open Knowledge Format v0.3

출처: https://github.com/open-knowledge-format/open-knowledge-format 의 `SPEC.md` (Apache-2.0)

### 내용

- 지식 묶음(bundle)은 Markdown 파일의 디렉터리다. 파일 하나가 개념 하나이고, YAML frontmatter와 본문으로 이뤄진다. Git 저장소 배포를 권장한다.
- 필수 필드는 `type` 하나뿐이다. 적합성 조건은 frontmatter가 YAML로 읽히는 것 정도로 매우 느슨하다.
- 확장: 명세에 없는 키를 어느 수준에든 추가할 수 있고, 소비자는 모르는 키를 거부하면 안 되며, 파일을 고치는 쪽은 모르는 키를 보존해야 한다. 자체 키는 `x-<producer>-<name>` 형식을 권장한다.
- 출처: `sources` 목록. 항목마다 `resource`(필수), `id`, `title`, `author`, `last_modified`. 본문의 각주 라벨을 `sources[].id`와 맞춰 문장 단위로 출처를 붙인다.
- 신뢰: `generated { by, at }`(누가 언제 작성)와 `verified [{ by, at }]`(누가 언제 확인)를 분리해 기록한다. 신뢰 등급은 저장하지 않고 계산한다: 미확인, 기계 확인, 사람 검토. **내용이 바뀐 뒤의 확인만 현재 등급에 반영한다.**
- 행위자 표기: 에이전트는 `<producer>/<version>`, 그 외는 `human:`, `team:`, `process:` 접두어.
- 수명: `status`(draft, stable, deprecated), `superseded_by`, `stale_after`(절대 시각).
- 검증된 계산(Attested Computation): 값을 계산하는 승인된 방법과, 그 방법으로 계산했는지 확인하는 결정적 코드를 지식으로 둔다.

### 명세에 없는 것

- 출처의 세부 위치(페이지, 문단, 셀, 타임코드)와 인용문
- 접근 권한. 신뢰 등급은 참고 신호일 뿐 접근 통제가 아니라고 명시한다
- 변경 제안과 승인 절차. Git의 PR에 맡긴다
- 개념 사이의 관계 유형. 링크는 유형 없는 방향 관계다
- 원본 변경 신호와 유효 기간. "다음 버전으로 미룸"에 올라 있다

1.0 이전이라 부 버전에서도 호환이 깨지는 변경이 있을 수 있다.

### gotgan에 주는 영향

| 항목 | 판단 |
| - | - |
| 지식 파일 형식 | **채택.** Vault의 `knowledge/`를 OKF v0.3 적합 묶음으로 만든다. 적합 조건이 느슨해서 비용이 거의 없고, OKF를 읽는 도구가 gotgan 지식을 그대로 읽는다 |
| 작성·확인 기록과 계산되는 신뢰 등급 | **채택.** 기존 안의 신뢰 등급 열거값 네 개를 저장하는 대신 `generated`와 `verified` 기록을 저장하고 등급은 계산한다. 자기 확인과 타인 확인은 두 행위자를 비교해 구분한다. 내용이 바뀌면 이전 확인이 무효가 되는 규칙도 그대로 쓴다 |
| 행위자 표기 | **채택** |
| `status`, `superseded_by`, `stale_after` | **채택** |
| 문장 단위 출처(각주 + `sources[].id`) | **채택.** 위치, 인용문, 원본 버전 해시는 `sources` 항목 안에 `x-gotgan-*` 확장 키로 넣는다 |
| 원본 개정에 따른 재검증 표시 | 확장 키로 구현한다. 명세가 다루기 시작하면 맞춘다 |
| 접근 등급, 변경안, 승인 | OKF 밖이다. gotgan 고유 영역으로 유지한다 |
| 검증된 계산 | 지금은 채택하지 않는다. 엑셀 수치의 근거를 다룰 때 다시 검토한다 |

세부 필드 정의는 ADR-003에서 정한다. 명세 버전은 0.3으로 고정하고 Vault에 기록한다.

## 3. multica-ai/andrej-karpathy-skills

출처: https://github.com/multica-ai/andrej-karpathy-skills (MIT)

### 내용

코딩 에이전트의 흔한 실수를 줄이기 위한 행동 지침 파일 하나다. 지식 관리 도구가 아니다. 네 가지 원칙으로 이뤄진다.

1. 코딩 전에 생각한다: 가정을 밝히고, 해석이 여럿이면 제시하고, 모르면 멈추고 묻는다.
2. 단순함이 먼저다: 요청받지 않은 기능, 한 번 쓰는 코드의 추상화, 요청받지 않은 설정 가능성을 넣지 않는다.
3. 필요한 곳만 고친다: 주변 코드를 "개선"하지 않는다. 바뀐 줄은 모두 요청과 직접 이어져야 한다.
4. 목표 중심으로 실행한다: 검증 가능한 성공 기준을 정하고 통과할 때까지 반복한다.

### gotgan에 주는 영향

- **개발 방식**: 이 저장소에서 일하는 에이전트의 작업 지침으로 채택한다. 저장소의 `CLAUDE.md`에 한국어로 옮기고 계획 단계에 맞는 항목을 더했다.
- **계획 자체**: "단순함이 먼저다"를 계획에 적용하면, 제품 코드를 쓰기 전에 가설부터 싸게 확인하라는 결론이 나온다. 5절의 제안이 그것이다.

## 4. Relate (내장형 그래프 DB)

출처: https://github.com/relatedb/relate 의 `README.md`, `docs/limitations.md`, `clients/java/README.md` (Apache-2.0, 확인 시점 버전 1.3.x). 소개 영상(https://www.youtube.com/watch?v=sX1ezd8mtOE)은 제목만 확인했고 시청하지 못했다. 영상 제목에 나오는 `relate-agent-memory` 스킬은 이 저장소에서 찾지 못했다(미확인).

### 내용

- Rust로 만든 내장형 속성 그래프 엔진이다. 서버 없이 단일 실행 파일이나 라이브러리로 동작하고 Cypher로 질의한다.
- 저장 형태는 파일 하나(`.rl`), 디렉터리, 메모리 중 하나다.
- **마크다운 모드**: 그래프를 마크다운 폴더로 저장한다. 노드가 노트 하나이고, frontmatter의 `type`이 라벨, frontmatter 안의 `[[위키링크]]`가 관계다. 폴더를 편집기나 Git으로 다루면서 Cypher로 질의할 수 있다.
- 벡터 검색, 전문 검색, 둘을 섞은 검색을 지원한다고 적혀 있다.
- CLI, Python, Node.js, Rust 바인딩이 있고 MCP 서버로도 띄울 수 있다. 에이전트용 스킬을 설치하는 명령이 있다.
- 한계(문서에 명시): 단일 프로세스, 프로세스당 사용자나 에이전트 하나, 저장소당 그래프 하나, 그래프 전체가 메모리에 올라가야 한다.
- Java 클라이언트는 스스로 "spike"라고 표시하며, JNA로 네이티브 라이브러리를 불러 쓴다.

### gotgan에 주는 영향

기존 판단은 "그래프 DB는 필요가 측정되기 전에는 도입하지 않는다"였다. 그 이유의 절반은 서버 운영 부담이었는데, 내장형이면 그 부담이 없다. 그래서 판단을 다음과 같이 고친다.

| 항목 | 판단 |
| - | - |
| 파생 인덱스로 사용 | **후보로 채택, 기술 확인 실험 후 결정.** 지식 파일에서 그래프를 만들어 "이 파일을 근거로 한 지식", "이 지식과 연결된 신고와 결정" 같은 질의에 쓴다. 지워도 지식 파일에서 다시 만들 수 있어야 한다 |
| 검색 인덱스 겸용 | 후보. 전문 검색과 벡터 검색이 함께 있어 별도 인덱스를 두지 않아도 될 수 있다. 한국어 전문 검색 품질은 미확인 |
| 정본 저장소로 사용 | **채택하지 않는다.** Cypher로 쓰면 변경안과 승인 절차를 거치지 않고 지식이 바뀐다. 정본은 Git 커밋이라는 ADR-001과 충돌한다 |
| 마크다운 모드로 지식 폴더를 직접 열기 | 미정. Relate는 관계를 frontmatter의 `[[위키링크]]`로 적는데, OKF v0.3은 위키링크를 링크로 인정하지 않는다. 두 형식이 같은 파일에서 함께 성립하는지 실험으로 확인한다 |
| 에이전트 메모리로 사용 | 채택하지 않는다. 에이전트가 직접 쓰는 메모리는 검증되지 않은 내용이며, gotgan의 승인된 지식과 섞지 않는다 |
| 팀·기업 단계 | 단일 프로세스 제약 때문에 그대로는 쓸 수 없다. 인덱스 포트 뒤에 두어 교체할 수 있게 한다 |

### 기술 확인 실험

관문 G2 이전에 할 수 있는 일회용 실험이다. 각 항목은 통과 여부를 판정할 수 있다.

1. OKF 형식의 지식 파일 20개 안팎을 Relate에 적재하고, "특정 원본 파일을 근거로 한 지식 목록"을 Cypher 한 문장으로 얻는다.
2. 마크다운 모드로 OKF 묶음을 열었을 때 읽히는지, Relate가 파일을 쓴 뒤에도 OKF 적합 조건이 유지되는지 확인한다.
3. Java에서 호출하는 경로 두 가지(JNA 클라이언트, CLI를 하위 프로세스로 실행)를 각각 시도하고 설치 절차와 실패 지점을 기록한다.
4. 네트워크를 끊은 상태에서 설치와 실행이 되는지 확인한다.
5. 한국어 문장으로 전문 검색을 해서 조사 붙은 단어가 검색되는지 확인한다.

1번이 실패하면 채택하지 않는다. 3번이 둘 다 불안정하면 1단계에서는 관계 테이블로 시작하고 Relate는 미룬다.

## 5. 계획에 대한 제안: 코드 없는 사전 실험

참고한 영상의 설명문에 따르면, 영상은 기존 저장소에 신고 스킬과 큐레이터 스킬을 붙여 "규칙이 없어 멈춘 에이전트가 큐레이터 실행 뒤에는 규칙대로 고치는" 한 바퀴를 보여 준다. 같은 방식이면 gotgan의 핵심 가설을 제품 코드 없이 먼저 확인할 수 있다.

**방법**

1. 대표 자료를 폴더에 둔다(조건 A).
2. 기존 코딩 에이전트에 신고 스킬과 큐레이터 스킬을 준다. 큐레이터는 OKF 형식의 Markdown 지식 파일을 만들고, 문장마다 출처를 붙인다.
3. 사람이 큐레이터의 변경을 Git 비교 화면으로 검토하고 승인한다.
4. 같은 질문을 지식이 없을 때와 있을 때(조건 C) 각각 묻고 비교한다.

**얻는 것**

- 큐레이션이 정확도를 올리는지를 몇 주가 아니라 며칠 안에 본다.
- 어떤 유형의 지식이 실제로 쓸모 있는지 알게 되어 ADR-003을 근거를 갖고 쓸 수 있다.
- 사람이 검토하는 데 드는 시간을 실제로 재 볼 수 있다.

**확인하지 못하는 것**

- 인용문 실재 검사, 원본 버전 관리, 권한. 이것들은 제품 코드가 필요하다.
- HWPX와 XLSX 처리. 에이전트가 직접 읽을 수 있는 형식(텍스트, PDF)으로만 실험한다.

**트레이드오프**: 사전 실험을 하면 1단계 착수가 그만큼 늦어진다. 반면 가설이 약하다고 나오면 Vault 규격과 큐레이션 설계에 들일 시간을 아낀다. 채택 여부는 프로젝트 소유자가 정한다.
