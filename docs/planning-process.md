# 계획 수립과 검토 절차

코드를 쓰기 전에 무엇을 문서로 확정하고, 각 문서를 어떻게 검토해 승인하는지 정한다.

## 1. 현재 계획의 빈 곳

[개발 계획](plan.md)은 방향과 단계 순서만 담고 있다. 다음이 비어 있다.

| 빈 곳 | 없으면 생기는 문제 |
| - | - |
| 첫 사용자와 핵심 사용 시나리오 | 무엇을 먼저 만들지 판단할 기준이 없다 |
| 비목표(하지 않을 것) | 범위가 다시 불어난다 |
| 평가 설계(자료, 질문 유형, 채점, 합격 기준) | A/B/C 실험 결과를 해석할 수 없다 |
| Vault 규격(디렉터리, 파일 형식, 식별자) | 수집과 큐레이션 구현이 서로 다른 가정을 한다 |
| 도메인 모델(Aggregate, 불변식, 이벤트) | 모듈 경계가 구현 중에 흔들린다 |
| 위험 목록과 대응 | 기술 위험(HWP 파싱, 내부 LLM 성능 등)을 늦게 발견한다 |
| 단계별 작업 분해 | 진행 상황과 남은 일을 알 수 없다 |

## 2. 작성할 문서와 순서

앞 문서가 뒤 문서의 전제이므로 순서대로 작성하고 승인한다.

| 순서 | 문서 | 담는 내용 |
| - | - | - |
| 1 | `docs/01-product-definition.md` | 첫 사용자, 핵심 시나리오 3~5개, 비목표, 성공 기준 |
| 2 | `docs/02-evaluation-design.md` | 대표 자료, 질문 유형과 수량, 정답 근거 작성 방법, 채점 방식, 합격·기각 기준 |
| 3 | `docs/adr/0001`~`0004` | 정본·일관성, 배포 등급별 정책과 저장 구성, 지식 단위와 근거 앵커, 권한 전파 |
| 4 | `docs/03-vault-spec.md` | 디렉터리 구조, 파일 형식, 식별자, 스키마 버전 |
| 5 | `docs/04-domain-model.md` | Bounded Context, Aggregate, 불변식, 이벤트, 컨텍스트 간 계약 |
| 6 | `docs/05-risks.md` | 위험, 발생 가능성과 영향, 조기 확인 방법, 대응 |
| 7 | `docs/06-phase1-breakdown.md` | 1단계 작업 분해와 완료 조건. 2단계 이후는 1단계 결과를 보고 작성한다 |

## 3. 문서 하나의 검토 절차

모든 문서는 PR 하나로 올리고 다음을 거친다.

1. **초안 작성**: 초안 PR로 올린다. 확인하지 못한 내용은 "미확인"으로 표시한다.
2. **자체 점검**: 4절의 점검표를 작성자가 확인하고 결과를 PR 본문에 적는다.
3. **독립 검토**: 작성 과정을 모르는 검토자가 문서만 읽고 반론과 누락을 찾는다. 검토자는 문서를 고치지 않고 의견만 남긴다.
4. **반영**: 작성자가 의견마다 수용, 기각(사유 포함), 보류 중 하나로 답한다.
5. **결정**: 프로젝트 소유자가 남은 쟁점을 결정하고 병합한다. 병합이 승인이다.

작성자와 독립 검토자는 서로 다른 주체여야 한다. 에이전트가 작성한 문서는 별도 맥락의 에이전트나 사람이 검토한다. 이 프로젝트가 지식에 적용하려는 "작성·검증·승인 분리"를 계획 문서에도 그대로 적용한다.

## 4. 점검표

- 전제를 명시했는가. 확인된 사실과 가정을 구분했는가.
- 각 결정에 대안과 트레이드오프를 적었는가.
- 주장마다 검증 방법이 있는가. 어떤 결과가 나오면 기각하는지 적었는가.
- 승인된 다른 문서와 모순되지 않는가.
- 비목표에 해당하는 내용이 들어오지 않았는가.
- 다음 문서를 쓰는 데 필요한 결정이 빠지지 않았는가.
- 수치나 성능 주장에 출처나 측정 계획이 있는가.

## 5. 관문

| 관문 | 통과 조건 | 통과 후 가능한 일 |
| - | - | - |
| G0 | 제품 정의 승인 | 평가 설계, ADR 검토 |
| G1 | 평가 설계 승인, 평가셋 동결 | 기준선 실험 준비 |
| G2 | ADR 4건, Vault 규격, 도메인 모델 승인 | 코드 작성 시작 |
| G3 | 위험 목록, 1단계 작업 분해 승인 | 1단계 착수 |

G2 이전에는 기술 위험을 확인하는 일회용 실험 코드만 작성한다. 예: HWPX 표 추출, JGit 동작 확인.

## 6. 승인 후 변경

- 승인된 문서는 PR로만 고치고 같은 검토 절차를 거친다.
- ADR은 고치지 않는다. 결정을 바꿀 때는 새 ADR을 쓰고 이전 ADR의 상태를 "대체됨"으로 바꾼다.
- 단계가 끝날 때마다 계획 문서를 실제 결과와 대조해 갱신한다.
