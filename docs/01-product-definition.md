# 제품 정의

- 상태: 초안 (2판)
- 날짜: 2026-11-28
- 1판(2026-11-27)은 소스코드 저장소에서 에이전트의 규칙 준수를 올리는 것을 중심에 두었다. 실험 결과에 따라 방향을 바꿔 다시 썼다. 1판은 Git 이력에 있다.

무엇을, 누구를 위해, 어디까지 만드는지 정한다. 이후의 ADR, Vault 규격, 도메인 모델은 이 문서를 전제로 한다.

## 1. 한 줄 정의

gotgan은 문서 묶음을 전부 읽어 **무엇이 지금 유효하고 어디가 낡았거나 서로 어긋나는지**를 근거와 함께 판정하고, 주제별 자료 안내로 구성해 현황판으로 보여 주며, 문서를 고친 뒤의 변화를 추적하는 도구다.

## 2. 이 정의의 근거

두 실험의 결과다. 수치의 출처는 [사전 실험](../experiments/pre/README.md) 10절과 [문서 폴더 전수 검토](../experiments/doc/REVIEW.md) 7절이다.

| 처음의 가설 | 결과 |
| - | - |
| 검증된 지식을 만들어 두면 에이전트가 규칙을 더 잘 지킨다 | 문서화가 잘된 소스코드 저장소에서는 보이지 못했다. 지식 없이도 위반이 적었다(2/29, 3/24). 지식이 겨냥한 과제에서 탐색 비용은 줄었다 |
| 큐레이터 에이전트가 지식을 쓴다 | 처음 쓴 지식은 대부분 원문과 어긋났다(9건 중 5건, 25건 중 20건). 여러 원문을 종합해 규칙을 새로 쓰는 유형은 고쳐도 수렴하지 않았다 |

실제로 값을 낸 것:

| 한 일 | 결과 |
| - | - |
| 문서 314건을 전부 읽고 판정 | 문제 84건을 올렸고, 대조 검증 뒤 61건이 남았다 |
| 작성자와 다른 에이전트의 대조 검증 | 틀린 판정 23건과 어긋난 지식 20건을 걸러냈다 |
| 문서 수정과 재판정 | 56건을 해결해 남은 문제가 61건에서 2건이 됐다 |
| 현황판 | 상태, 주제별 지식, 근거, 원문의 해당 줄, 이력을 한 파일로 보여 줬다 |

이 결과는 대상 하나(Markdown과 HTML 위주의 문서 폴더), 외부 LLM, 실험용 스크립트와 사람이 이어 붙인 절차로 얻은 것이다. 다른 대상에서 같은 결과가 나온다는 보장은 없다.

## 3. 확인된 조건

프로젝트 소유자가 직접 밝힌 것이다.

1. 개인용으로 시작하되 팀 사용을 고려한다.
2. 당분간 외부 LLM API로 진행한다.
3. 검토 결과를 시각화로 잘 보이게 한다.
4. 얼마나 잘 정리됐는지와 계속 개선되는지를 볼 수 있어야 한다.
5. 지식에서 그 원천을 찾아갈 수 있어야 한다.
6. 검증된 가치(문서 점검, 검증, 현황판)를 먼저 제품으로 만들고, 처음의 가설은 에이전트가 직접 읽기 어려운 자료에서 따로 실험한다.

## 4. 사용자

| 구분 | 대상 | 취급 |
| - | - | - |
| 1차 | 문서 묶음을 가진 프로젝트를 혼자 맡은 사람. 문서가 수백 건이고 무엇이 최신인지 본인도 확신하지 못한다 | 초기 범위의 구현 대상 |
| 2차 | 같은 문서 묶음을 함께 쓰는 팀 | 구현은 뒤로. 설계가 막지 않도록 한다 |

팀을 고려해 처음부터 지키는 것: 모든 판정과 변경에 행위자를 기록한다. 항목의 식별자는 한 번 정하면 바꾸지 않고 묶음을 합쳐도 충돌하지 않게 만든다. 저장소, 인덱스, LLM은 포트 뒤에 둔다. 유스케이스를 CLI에 묶지 않는다.

## 5. 핵심 고리

```
변환 → 전수 검토 → 대조 검증 → 지식 구성 → 현황판
                                              ↓
            현황판 갱신 ← 재판정 ← 수정 ← 수정 계획(사람 승인)
```

한 바퀴가 돌 때마다 이력에 한 줄이 쌓인다. "계속 개선되는가"는 이 이력으로 본다.

## 6. 시나리오

"확인"은 실험에서 한 번 이상 끝까지 해 본 것이고, "미확인"은 아직 해 보지 않은 것이다.

| ID | 시나리오 | 완료 조건 | 상태 |
| - | - | - | - |
| S1 | **변환**. 문서 묶음을 위치 표시가 붙은 텍스트로 바꾼다 | 모든 파일이 성공, 부분 추출, 실패 중 하나로 보고되고 뒤의 둘은 사유가 있다. 원본은 바뀌지 않는다 | Markdown, HTML 확인. HWPX, XLSX, PDF는 시험 파일로만 확인 |
| S2 | **전수 검토**. 문서마다 종류, 날짜, 주제, 상태를 판정하고 문제를 올린다 | 모든 문서가 여섯 상태 중 하나를 가진다. 문제마다 원문 그대로의 인용이 있다. 근거를 대지 못한 판정은 "판단 불가"다 | 확인 |
| S3 | **대조 검증**. 판정을 쓴 쪽과 다른 에이전트가 원문과 대조한다 | 문제 전부와 지식 전부가 일치, 불일치, 판단 불가 중 하나를 받는다. 다시 검증할 때 이전 검증자를 이어 쓰지 않는다 | 확인 |
| S4 | **지식 구성**. 주제마다 자료 안내를 만든다 | 주제마다 정본, 함께 볼 문서, 유효하지 않은 문서, 알려진 어긋남이 있다. 모든 문단에 인용이 있고 인용문 검사가 실패 0건이다 | 확인 |
| S5 | **현황판**. 상태와 변화를 한 화면에서 본다 | 문서 상태, 주제별 지식, 문제 목록, 이력이 나온다. 주제에서 지식 본문, 근거, 원문의 해당 줄까지 화면 안에서 이동한다. 네트워크 없이 열린다 | 확인 |
| S6 | **수정 계획**. 문제마다 무엇이 맞는지 확인하고 고칠 방법을 정한다 | 맞는 쪽을 코드나 설정 같은 실제 근거로 확인한다. 문제를 수정, 사람 결정 필요, 원본이 아닌 쪽이 틀림, 문제 아님으로 나눈다. 사람이 승인하기 전에는 원본을 고치지 않는다 | 확인 |
| S7 | **재판정**. 고친 뒤 실제로 해소됐는지 확인한다 | 수정에 참여하지 않은 에이전트가 문제별로 해소 여부와 새 어긋남을 판정한다. 바뀐 문서를 인용한 지식이 갱신되고 다시 검증된다 | 확인 |
| S8 | **이력**. 검토할 때마다 현행 문서 수와 남은 문제 수가 쌓인다 | 이전 검토와의 차이가 현황판에 나온다. 남은 문제 수가 산식으로 검산된다 | 확인(세 줄) |
| S9 | **에이전트의 사용**. 에이전트가 자료 안내를 읽고 일하며, 지식이 없거나 틀리면 신고한다 | 에이전트는 지식과 원본을 직접 고치지 못한다. 신고가 다음 검토의 입력이 된다 | 신고는 확인. 지식이 일의 정확도를 올리는지는 미확인 |

## 7. 실험에서 얻은 규칙

제품이 설정으로 끌 수 없게 한다. 각 규칙은 그것이 없을 때 생긴 오류에서 나왔다.

| 규칙 | 근거 |
| - | - |
| 판정과 지식에는 원문 그대로의 인용이 있어야 한다. 없으면 판단 불가다 | 인용 없는 요약은 검증할 방법이 없다 |
| 쓴 쪽과 검증하는 쪽은 다른 주체다. 사람의 승인은 대조 검증을 통과한 것만 받는다 | 인용문 검사와 사람 승인을 모두 통과한 지식 9건 중 5건이 틀렸다 |
| 문제는 표본이 아니라 전부 대조 검증한다 | 표본의 오류율은 20%였는데 나머지는 37%였다 |
| 지식은 "어디에 무엇이 적혀 있는가"만 적는다. 여러 원문을 종합해 규칙을 새로 쓰지 않는다 | 규칙 유형 3건은 두 번 고쳐도 원문과 어긋나 폐기했다 |
| 원문이 말한 범위와 시점을 넘겨 쓰지 않는다 | 가장 흔한 오류였다 |
| 문서와 다른 근거가 어긋날 때 문서가 틀렸다고 가정하지 않는다 | 코드가 틀린 것으로 확인된 사례가 있었다 |
| 원본을 고치는 일은 사람이 계획을 승인한 뒤에 한다 | 원본은 사용자의 것이다 |
| 수정은 재판정을 거쳐야 해결로 기록된다 | 수정 56건 중 12건이 한 번에 해소되지 않았고, 수정이 새 문제 6건을 만들었다 |
| 항목의 식별자를 바꾸지 않는다 | 번호가 밀려 검증 결과가 다른 항목에 붙었다 |
| 사라진 인용을 비슷한 문장으로 자동 대체하지 않는다 | 자동으로 고른 12건 중 7건이 엉뚱한 줄이었다 |

## 8. 제품이 맡을 일

실험에서는 사람과 진행 세션이 절차 문서를 보고 손으로 이어 붙였다. 제품은 이 부분을 맡는다. 판정과 수정안 작성 자체는 LLM이 한다.

| 제품이 맡는 것 | 실험에서 드러난 필요 |
| - | - |
| 단계의 순서와 에이전트 격리 | 검증자가 판정자의 설명을 보지 않아야 하고, 이전 검증자를 재사용하면 안 된다 |
| 검토 상태의 저장과 식별자 관리 | 항목 번호가 밀리는 사고가 두 번 있었다 |
| 인용의 위치 추적 | 문서 41개를 고치자 지식 25건 중 20건을 손봐야 했다. 줄 번호만 밀린 것은 자동으로 갱신하고, 문장이 바뀐 것은 다시 쓸 대상으로 표시한다 |
| 집계와 검산 | 남은 문제 수가 한 번 틀렸다 |
| 현황판 생성 | |
| 비용과 시간의 기록 | 단계별 토큰을 사후에 모으느라 빠진 값이 있었다 |
| 사람 승인 지점 | 수정 계획, 사람 결정이 필요한 문제 |

## 9. 비목표

**하지 않는다**

- 채팅 서비스, 답 생성 기능, 자체 에이전트 엔진
- 여러 원문을 종합한 규칙이나 요약 지식의 자동 생성
- 사람의 승인 없는 원본 수정
- 실시간 공동 편집
- 서버로 운영하는 그래프 DB

**초기 범위에서 하지 않고 나중에 검토한다**

- 팀 기능: 다중 사용자 인증, 서버 측 권한, 동기화
- Knowledge Canvas, 문서 산출물 생성, 프로젝트 관리 모듈
- OCR, 음성 인식
- 원본이 문서가 아닌 대상(코드 주석 등)의 전수 검토

## 10. 처음의 가설을 어떻게 다루는가

"검증된 지식이 있으면 에이전트가 더 정확하게 일한다"는 기각된 것이 아니라 맞는 대상에서 시험해 보지 못한 것이다. 에이전트가 직접 읽기 어려운 자료(HWPX, XLSX, 스캔이 아닌 PDF, 회의록)에서 [문서 실험](../experiments/doc/README.md)의 절차로 확인한다. 자료는 소유자가 준비한다.

- 지지되면 S9를 넓힌다: 에이전트용 검색, MCP, 지식 유형의 확대를 검토한다.
- 지지되지 않으면 S9는 신고 수집에 머물고, 제품은 문서 점검 도구로 남는다.

어느 쪽이든 1~9절의 범위는 바뀌지 않는다.

## 11. 재는 것

실험의 값을 첫 기준선으로 둔다. 목표 수치는 두 번째 대상에서 한 번 더 잰 뒤에 정한다.

| 지표 | 계산 | 실험의 값 |
| - | - | - |
| 첫 판정의 오류율 | 대조 검증에서 불일치로 나온 문제의 비율 | 84건 중 23건(27%) |
| 첫 지식의 오류율 | 대조 검증에서 불일치로 나온 지식의 비율 | 25건 중 20건 |
| 검증끼리의 일치 | 같은 문제를 다른 검증자가 다시 봤을 때 같은 판정의 비율 | 8건 중 7건 |
| 수정의 재작업률 | 재판정에서 한 번에 해소되지 않은 비율 | 56건 중 12건(21%) |
| 남은 문제의 추이 | 검토마다의 남은 문제 수 | 61 → 49 → 2 |
| 지식 유지 비용 | 문서 수정 한 회차에 손본 지식의 비율 | 문서 41개 수정에 지식 25건 중 20건 |
| 문서당 비용 | 전 과정의 토큰을 문서 수로 나눈 값 | 약 3만 6천~3만 9천 토큰 |
| 사람의 시간 | 승인과 결정에 쓴 시간 | 재지 못했다 |

## 12. LLM 사용 방침

개발과 실험은 외부 LLM API로 한다. LLM 호출은 포트 뒤에 둔다. 변환, 인용문 검사, 집계, 현황판 생성은 LLM 없이 동작한다.

외부로 보내도 되는 자료만 쓴다. 가려야 할 내용은 변환 전에 원본에서 지운다. 인증서와 키 파일은 변환 대상에서 뺀다. 폐쇄망 동작과 내부 모델에서의 품질은 따로 검증하며, 외부 모델로 얻은 11절의 값은 내부 모델에 그대로 적용되지 않는다.

## 13. 가정과 미확인 사항

| 항목 | 현재 상태 | 정하는 곳 |
| - | - | - |
| 다른 문서 묶음에서도 같은 결과가 나오는가 | 대상 하나에서만 확인 | 두 번째 대상에서의 검토 |
| HWPX, XLSX, PDF의 변환 품질 | 공개 시험 파일과 작은 생성 파일로만 확인 | 오피스 문서 실험 |
| 문서 수가 수천 건일 때의 비용과 시간 | 미확인. 314건에 약 1,200만 토큰이 들었다 | 규모 실험 |
| 내부 모델에서의 판정 품질 | 미확인 | 내부 모델 전환 시 |
| 사람의 승인에 드는 시간 | 재지 못했다 | 다음 검토부터 기록 |
| 검토 상태를 어디에 어떤 형식으로 저장하는가 | 실험에서는 JSON 한 파일 | ADR-001 개정, Vault 규격 |
| 1차 사용자가 소유자 본인인가, 개발 인원, 팀으로 넓히는 시점 | 미확인 | 소유자 확인 |
