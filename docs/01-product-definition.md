# 제품 정의

- 상태: 초안 (독립 검토 1회, 참고 자료 분석 반영)
- 날짜: 2026-11-27

무엇을, 누구를 위해, 어디까지 만드는지 정한다. 이후의 평가 설계, ADR, Vault 규격은 이 문서를 전제로 한다. 단계(1~4단계)와 실험 조건(A/B/C)의 정의는 [개발 계획](plan.md)을 따른다.

## 1. 한 줄 정의

gotgan은 프로젝트 자료를 수집해 **근거를 확인할 수 있는 지식**으로 관리하고, 사람과 에이전트가 같은 지식을 쓰게 하는 파일 기반 지식 창고다.

"지식으로 관리"하는 부분은 큐레이션이 가치 있다는 가설에 의존한다. 2단계 실험에서 가설이 기각되면 S1·S2 중심의 "원본 + 인덱스 + 근거 확인" 제품으로 전환하고 이 문서를 개정한다.

## 2. 확인된 조건

프로젝트 소유자가 직접 밝힌 것은 다음 세 가지다. 이 문서의 나머지는 이 조건에서 도출한 제안이거나 가정이며, 가정은 10절에 모았다.

1. 개인용으로 시작하되 팀 사용을 고려한다.
2. 당분간 외부 LLM API로 테스트한다.
3. 평가용 자료는 소유자가 준비한다.

## 3. 사용자

| 구분 | 대상 | 취급 |
| - | - | - |
| 1차 | 개인 1인. 자기 프로젝트 자료를 직접 관리한다 | 1~3단계의 유일한 구현 대상 |
| 2차 | 팀. 공유 Vault를 함께 쓴다 | 구현은 4단계. 설계가 막지 않도록 한다 |
| 범위 밖 | 기업(복수 Vault, 중앙 권한·감사) | 이 문서에서 다루지 않는다. 팀 구현 뒤에 검토한다 |

### "팀을 고려한다"의 의미

나중에 추가하면 기존 데이터를 고쳐야 하는 것은 지금 지키고, 포트 구현이나 기능 추가로 붙일 수 있는 것은 미룬다.

**지금 지킨다 (1단계부터)**

| 항목 | 내용 |
| - | - |
| 행위자 기록 | 모든 변경에 행위자를 남긴다. 표기는 OKF v0.3을 따른다: 사람은 `human:<id>`, 에이전트는 `<이름>/<버전>`. 에이전트가 대리한 사람은 확장 필드로 함께 기록한다. Git author 문자열에 의존하지 않는다 |
| 접근 등급 | 원본과 지식의 메타데이터에 접근 등급을 둔다. 빈 값을 허용하지 않고, 수집 시 Vault의 기본 등급을 명시적으로 기록한다. 값 체계와 상속 규칙은 ADR-004에서 정한다 |
| 반출 가능 여부 | 접근 등급과 별도로 "외부 전송 가능" 표시를 둔다 (7절) |
| 작성·확인 기록 | 지식마다 누가 언제 작성했는지(`generated`)와 누가 언제 확인했는지(`verified`)를 기록한다. 신뢰 등급은 저장하지 않고 이 기록에서 계산한다. 내용이 바뀌면 그 전의 확인은 현재 등급에 반영하지 않는다. 자기 확인과 타인 확인은 두 행위자를 비교해 구분한다 |
| 지식 파일 형식 | OKF v0.3에 적합한 Markdown으로 쓴다. gotgan 고유 필드는 확장 키로 넣는다. 세부는 ADR-003에서 정한다 |
| 식별자 | Vault를 합쳐도 충돌하지 않는 식별자를 쓴다 |
| Vault 구성원 | Vault는 식별자와 구성원 목록을 가진다. 개인 Vault는 구성원이 한 명인 경우다 |
| 규격 버전 | Vault와 각 파일에 규격 버전을 기록한다 |
| 원본과 이력의 분리 | 원본 바이너리는 Git 이력에 넣지 않는다. 파기 요구가 생겼을 때 이력을 다시 쓰지 않기 위해서다 (ADR-001) |
| 질의 로그 | 검색·질의 기록에 행위자와 Vault 식별자를 남긴다 |
| 포트 | 저장소, 검색 인덱스, LLM은 포트 뒤에 둔다 |
| 유스케이스 | CLI에 묶지 않는다. 서버에서 같은 유스케이스를 호출할 수 있어야 한다 |

## 4. 풀려는 문제

아래는 기획 논의에서 추정한 것이며 실제 사용으로 확인되지 않았다.

1. 프로젝트 자료가 여러 형식과 위치에 흩어져 있어, 현재 유효한 내용이 무엇인지 찾기 어렵다.
2. LLM이 답을 주어도 그 근거를 원본에서 확인하기 어렵다.
3. 같은 질문을 할 때마다 원본을 처음부터 다시 탐색한다.
4. 문서끼리 내용이 상충하거나 개정되어도 알아차리지 못한다.

## 5. 핵심 시나리오

### 답을 만드는 주체

gotgan은 답을 생성하지 않는다. gotgan은 검색 결과와 근거(원본 버전, 위치, 인용문)를 돌려주고, 답은 gotgan의 CLI를 쓰는 에이전트가 만든다. 실험의 재현성을 위해 평가 하네스(`eval/`)에 고정된 기준 에이전트를 둔다. gotgan은 대화 상태나 채팅 화면을 갖지 않는다.

### 시나리오

| ID | 시나리오 | 완료 조건 | 단계 |
| - | - | - | - |
| S1 | **자료 수집**. 폴더를 지정하면 문서를 수집한다 | (1) 저장된 원본의 해시가 입력 파일과 같다. (2) 해시가 같은 파일은 한 번만 저장된다. (3) 모든 입력 파일이 "성공", "부분 추출", "실패" 중 하나로 보고되고, 뒤의 둘은 사유가 붙는다. 텍스트 없는 스캔 PDF, 읽지 못한 표나 시트는 부분 추출로 보고한다 | 1 |
| S2 | **근거 검색**. 질의하면 근거 후보를 받는다 | (1) 각 결과가 원본 ID, 버전, 위치, 인용문을 가진다. (2) 근거 ID로 `inspect`를 실행하면 그 버전 그 위치의 원문이 출력되고 인용문과 일치한다. (3) 일치하는 근거가 없으면 빈 결과를 돌려준다 | 1 |
| S3 | **원본 버전 수집**. 이미 수집한 문서의 개정본을 수집한다 | 새 버전이 같은 문서의 다음 버전으로 등록되고 이전 버전도 조회된다. 검색 결과는 어느 버전인지 표시한다 | 1 |
| S4 | **에이전트의 읽기**. 에이전트가 CLI로 검색하고 근거를 확인해 답한다 | 기준 에이전트가 CLI만으로 평가 질문에 답하고, 답에 근거 ID를 붙인다. 근거를 찾지 못하면 "근거 없음"으로 답한다 | 1 |
| S5 | **지식 승격**. 반복해서 쓰일 내용을 변경안으로 제안하고 검증·승인해 반영한다 | (1) 변경안의 모든 인용문이 원본의 해당 위치에 실재하는지 자동 검사를 통과한다. (2) 작성 행위자와 확인 행위자가 기록된다. (3) 승인 뒤 대상이 바뀌었으면 반영이 거부된다. (4) 반영을 되돌리는 변경안을 만들 수 있다 | 2 |
| S6 | **에이전트의 변경안 제출**. 에이전트가 CLI로 변경안을 제출한다 | (1) CLI는 정본을 직접 쓰는 명령을 제공하지 않는다. (2) 절차를 거치지 않은 정본 변경은 `verify`가 찾아낸다. (3) 승인 행위자는 사람이어야 한다 | 2 |
| S7 | **개정 영향 확인**. 원본이 개정되면 영향받는 지식을 확인한다 | 2단계: 특정 원본 버전을 근거로 한 지식의 목록을 조회할 수 있다. 3단계: 새 버전 수집 시 해당 지식이 자동으로 "재검증 필요"로 표시되고 검색 결과에 그 상태가 나온다 | 2, 3 |
| S9 | **누락·오류 신고**. 에이전트나 사람이 필요한 지식이 없거나 틀렸다고 신고한다 | (1) 신고가 행위자, 당시의 질의, 대상 지식과 함께 Vault에 기록된다. (2) 신고 목록을 조회할 수 있다. (3) 변경안이 신고를 참조하고, 반영되면 그 신고가 처리됨으로 바뀐다 | 2 |
| S8 | **MCP와 근거 뷰어**. 에이전트는 MCP로, 사람은 웹 화면으로 같은 기능을 쓴다 | MCP 도구가 CLI와 같은 유스케이스와 제약을 따른다. 뷰어에서 지식과 원본을 나란히 열고 인용 위치가 강조된다 | 3 |

S3에서 "같은 문서의 개정본"을 판정하는 규칙(같은 경로, 사용자 지정 등)은 Vault 규격에서 정한다. S7에서 인용 구간이 바뀌지 않은 지식까지 표시할지는 ADR-003에서 정한다.

S9의 신고는 무엇을 지식으로 올릴지 정하는 첫 번째 입력이다. 모든 원본을 미리 정리하지 않고, 작업 중에 막힌 곳부터 채운다.

로컬 파일 시스템에서는 에이전트가 파일을 직접 고치는 것을 막을 수 없다. 그래서 S6은 차단이 아니라 "수단을 제공하지 않고, 우회하면 탐지한다"를 조건으로 삼는다. 차단은 4단계의 서버 측 강제에서 다룬다.

### 단계별 지원 형식

| 단계 | 형식 |
| - | - |
| 1단계 전반 | 텍스트, Markdown, 텍스트 레이어가 있는 PDF |
| 1단계 후반 | HWPX, XLSX |
| 범위 밖 | 스캔 문서 OCR, HWP(구 형식), 녹음 파일 |

A/B 기준선 측정은 네 형식이 모두 수집된 뒤에 한다.

## 6. 비목표

**하지 않는다**

- 채팅 서비스, 대화 상태 관리
- 답 생성 기능과 자체 에이전트 엔진
- 실시간 공동 편집
- 그래프 DB. 관계 질의가 느리다고 측정되기 전에는 도입하지 않는다

**1~3단계에서 하지 않고 4단계에서 검토한다**

- Knowledge Canvas, 관계 그래프 화면, 블록 편집기
- 문서 산출물 생성(Word, Excel, PowerPoint, HWP)
- SI 프로젝트 관리 모듈과 외부 시스템 연동
- OCR, 녹음 파일의 STT와 화자 분리

## 7. LLM 사용 방침

개발과 실험은 외부 LLM API로 진행한다. "외부 API 없이 동작한다"는 원칙은 유지하되 검증 시점을 뒤로 둔다.

### 기능별 LLM 의존

| 구분 | 기능 |
| - | - |
| LLM 불필요 | 수집, 파싱, 키워드 검색, `inspect`, 무결성 검사(`verify`), 인용문 실재 검사, 변경안 작성(사람), 승인, 반영, 개정 영향 조회 |
| LLM 선택 | 임베딩 기반 검색 |
| LLM 필수 | 에이전트의 답 생성, 지식 후보 자동 추출, 함의 검사 |

1단계의 조건 B는 키워드 검색을 기본으로 한다. 임베딩 검색을 별도 조건으로 추가할지는 평가 설계에서 정한다. 외부 임베딩으로 만든 인덱스와 측정값은 내부 모델로 바꿀 때 다시 만들어야 한다.

### 외부 전송 통제

- 원본마다 "외부 전송 가능" 표시를 둔다. gotgan의 LLM 포트는 표시가 없는 자료가 포함된 요청을 외부 공급자로 보내지 않는다.
- 에이전트가 Vault를 읽어 자기 LLM으로 보내는 경로는 gotgan이 통제할 수 없다. 그래서 외부 LLM을 쓰는 에이전트에는 **전송 가능한 자료만 담긴 Vault**만 연결한다. 실험 기간의 평가용 Vault는 전부 전송 가능한 자료로 구성한다.
- 익명화가 필요하면 **수집 전에** 한다. 익명화한 사본이 그 Vault의 원본이다. 수집 후에 바꾸면 해시와 인용문 검사가 깨진다.

### 공급자 조건

- 공급자의 데이터 보존과 학습 사용 조건을 확인한 뒤 사용한다.
- 평가 기간에는 모델 버전을 고정하고 실행마다 기록한다.
- LLM 요청과 응답을 평가 하네스에 기록한다.
- 비용 상한은 평가 설계에서 정한다.

### 내부 모델 전환

폐쇄망 동작과 내부 모델 성능은 4단계 전에 따로 검증한다. 외부 모델로 얻은 결과는 내부 모델에 그대로 적용되지 않으므로 같은 평가셋을 다시 실행한다.

## 8. 성공 기준

수치는 평가 설계에서 정한다. 여기서는 무엇을 세는지 정한다.

| 대상 | 세는 것 |
| - | - |
| S1 | 입력 파일 중 상태가 보고되지 않은 파일 수(0이어야 한다). 부분 추출로 보고되지 않은 추출 누락 수 |
| S2 | 반환된 근거 중 인용문이 원문과 일치하지 않는 것의 수(0이어야 한다) |
| S4 | 답의 정확도. 근거가 답을 실제로 뒷받침하는 비율. 근거 없이 한 주장의 비율. 질문당 소요 시간과 토큰 |
| 큐레이션 가설 | 조건 C와 B의 위 지표 차이, 그리고 큐레이션에 든 시간. 합격선과 "재사용성"의 측정 방법은 평가 설계에서 정한다 |
| 제품 전체 | 1차 사용자가 자기 프로젝트 자료를 넣고 업무 질문에 쓴 횟수. 관찰 기간과 기준 횟수는 평가 설계에서 정한다 |

## 9. 대표 자료 요건

평가에 쓸 자료는 프로젝트 소유자가 준비한다.

- 형식: 회의록(텍스트), PDF, HWPX, XLSX를 각각 포함한다.
- 같은 주제의 개정본이 있다.
- 서로 상충하는 내용이 있는 문서 쌍이 있다.
- 여러 문서를 종합해야 답할 수 있는 주제가 있다.
- 전부 외부 API로 보낼 수 있다. 필요하면 수집 전에 익명화한다.
- 코드 저장소에 올리지 않는다. 별도 위치에 두고 해시 목록만 기록한다.

실제 자료로 개정본이나 상충 쌍을 채우지 못하면, 그 부분만 합성 자료로 보완하고 합성임을 표시한다.

평가 질문과 정답 근거는 **큐레이션을 시작하기 전에 동결한다.** 질문을 아는 사람이 큐레이션하면 조건 C에 정답이 새어 들어가기 때문이다. 1인 개발에서는 작성자를 나눌 수 없으므로 순서로 분리한다.
