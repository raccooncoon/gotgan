# 제품 정의

- 상태: 초안 (2판, 독립 검토 1회 반영)
- 날짜: 2026-11-28
- 1판(2026-11-27)은 소스코드 저장소에서 에이전트의 규칙 준수를 올리는 것을 중심에 두었다. 실험 결과에 따라 방향을 바꿔 다시 썼다. 1판은 Git 이력에 있다.

무엇을, 누구를 위해, 어디까지 만드는지 정한다. 이후의 ADR, Vault 규격, 도메인 모델은 이 문서를 전제로 한다.

## 1. 한 줄 정의

gotgan은 문서 묶음을 읽어 **무엇이 지금 유효하고 어디가 낡았거나 서로 어긋나는지**를 근거와 함께 판정하고, 주제별 자료 안내로 구성해 현황판으로 보여 주며, 문서를 고친 뒤의 변화를 추적하는 도구다.

## 2. 이 정의의 근거

두 실험의 결과다. 수치의 출처는 [사전 실험](../experiments/pre/README.md) 10절과 [문서 폴더 전수 검토](../experiments/doc/REVIEW.md) 7절이다.

### 처음의 가설

| 가설 | 결과 |
| - | - |
| 검증된 지식을 만들어 두면 에이전트가 규칙을 더 잘 지킨다 | 문서화가 잘된 소스코드 저장소에서는 보이지 못했다. 지식 없이도 위반이 적었다(2/29, 3/24) |
| 큐레이터 에이전트가 지식을 쓴다 | 처음 쓴 지식은 대부분 원문과 어긋났다(9건 중 5건, 25건 중 20건). 규칙 유형 4건 중 3건은 두 번 고쳐도 어긋나 폐기했다 |

지식이 겨냥한 과제에서는 도구 호출이 29%, 토큰이 18% 줄었다. 다만 실험 뒤에 추가로 본 지표이고, 회차당 한 번 돌렸으며, 지식이 그 과제의 신고에서 만들어진 가장 유리한 조건에서의 값이다. 지식이 다루지 않은 과제에서는 변화가 없었다.

### 한 대상에서 끝까지 해 본 것

문서 폴더 하나(314건, 대부분 Markdown과 HTML)에서 검토부터 수정까지 한 바퀴를 돌렸다.

| 한 일 | 결과 |
| - | - |
| 변환과 판정 | 314건 중 286건을 온전히, 11건을 일부만 변환했고 17건은 변환하지 못했다. 문제 84건을 올렸다 |
| 다른 에이전트의 대조 검증 | 84건 중 22건이 틀린 판정으로 나왔고, 검증끼리 갈린 1건을 소유자가 틀린 판정으로 확정해 61건이 남았다 |
| 문서 수정과 재판정 | 아래 집계 |
| 현황판 | 상태, 주제별 지식, 근거, 원문의 해당 줄, 이력을 한 파일로 보여 줬다 |

올라온 문제 84건과 수정 중에 생긴 6건을 합친 90건의 최종 상태:

| 상태 | 건수 |
| - | - |
| 문서를 고쳐 해결 | 56 |
| 틀린 판정이거나 고칠 필요가 없음 | 28 (대조 검증에서 23, 그 뒤 수정 계획 단계에서 5) |
| 수정이 만들었다가 같은 회차에서 해소 | 4 |
| 남음 | 2 |

남은 문제는 61건에서 2건이 됐다. 줄어든 59건 중 수정으로 해결한 것은 54건이고(해결 56건 가운데 2건은 수정이 만든 문제), 5건은 수정 계획을 세우다가 문제가 아니거나 고칠 필요가 없는 것으로 다시 분류한 것이다.

### 얻은 것과 든 것

| 얻은 것 | 든 것 |
| - | - |
| 대조 검증 뒤의 문제는 심각도 높음 1건, 중간 35건, 낮음 26건이었다(집계 시점 62건) | 토큰 약 1,130만~1,230만 |
| 수정 44건 중 28건은 옛 기록 문서에 정정 줄을 단 것이다 | 에이전트 실행 약 2시간 40분 |
| 문서 검토가 코드의 오류 1건을 찾았다 | 사람이 승인과 결정에 쓴 시간(재지 못했다) |

이 값이 든 비용에 견줘 충분한지는 아직 판단할 수 없다. 사람의 시간을 재지 않았고 대상이 하나뿐이다.

### 이 결과가 말하지 않는 것

- **놓친 문제가 얼마나 되는지.** 잰 것은 올린 문제 중 틀린 것의 비율뿐이다. 수정 계획을 세우다 범위 밖 어긋남 5건이 더 나왔고, 재판정에서 12건이 "같은 문서의 같은 서술을 놓침"으로 되돌아왔다. 놓친 것이 있다는 뜻이다.
- **다시 돌리면 같은 결과가 나오는지.** 같은 묶음을 두 번 검토해 보지 않았다.
- **판정이 실제로 맞는지.** "틀린 판정"은 대부분 다른 LLM 에이전트의 판정이다. 사람이 확인한 것은 일부다. 대조 검증을 통과한 61건 중에서도 5건이 나중에 문제가 아닌 것으로 드러났다.
- **제품이 이 품질을 재현하는지.** 실험은 범용 에이전트와 사람이 절차 문서를 보고 손으로 이어 붙였다.
- **다른 대상에서의 결과.** 대상 하나, 외부 LLM 하나의 결과다.

## 3. 확인된 조건

프로젝트 소유자가 직접 밝힌 것이다.

1. 개인용으로 시작하되 팀 사용을 고려한다.
2. 당분간 외부 LLM API로 진행한다.
3. 검토 결과를 시각화로 잘 보이게 한다.
4. 얼마나 잘 정리됐는지와 계속 개선되는지를 볼 수 있어야 한다.
5. 지식에서 그 원천을 찾아갈 수 있어야 한다.
6. 제시된 세 방향 가운데 "문서 점검·검증·현황판을 먼저 만들고, 처음의 가설은 에이전트가 직접 읽기 어려운 자료에서 따로 실험한다"를 골랐다.

## 4. 사용자

| 구분 | 대상 | 취급 |
| - | - | - |
| 1차 | 문서 묶음을 가진 프로젝트를 혼자 맡은 사람. 문서가 수백 건이고 무엇이 최신인지 본인도 확신하지 못한다 | 초기 범위의 구현 대상 |
| 2차 | 같은 문서 묶음을 함께 쓰는 팀 | 구현은 뒤로. 설계가 막지 않도록 한다 |

팀을 고려해 처음부터 지키는 것: 모든 판정과 변경에 행위자를 기록한다. 항목의 식별자는 한 번 정하면 바꾸지 않고 묶음을 합쳐도 충돌하지 않게 만든다. 저장소, 인덱스, LLM은 포트 뒤에 둔다. 유스케이스를 CLI에 묶지 않는다.

**초기 범위의 대상을 좁힌다.** 실험에서 수정까지 끝낸 것은 텍스트 원본(Markdown, HTML)이고 옆에 대조할 코드와 설정이 있는 저장소였다. 초기 범위는 이 조건을 만족하는 묶음이다. 회의록이나 HWPX, XLSX처럼 대조할 코드가 없고 원본을 텍스트로 고칠 수 없는 묶음은 검토와 현황판(S1~S5)까지만 대상으로 하고, 수정 고리(S6~S7)는 14절의 미결이 풀린 뒤에 다룬다.

## 5. 핵심 고리

```
변환 → 전수 검토 → 대조 검증 → 지식 구성 → 현황판
                                              ↓
            현황판 갱신 ← 재판정 ← 수정 ← 수정 계획(사람 승인)
```

한 바퀴가 돌 때마다 이력에 한 줄이 쌓인다. "계속 개선되는가"는 이 이력으로 본다.

## 6. 시나리오

"수행"은 한 대상에서 한 번 끝까지 해 봤다는 뜻이다. 완료 조건을 처음부터 지켰다는 뜻이 아니며, 어긴 것은 비고에 적었다.

| ID | 시나리오 | 완료 조건 | 초기 범위 | 상태 |
| - | - | - | - | - |
| S1 | **변환**. 문서 묶음을 위치 표시가 붙은 텍스트로 바꾼다 | 모든 파일이 성공, 부분 추출, 실패 중 하나로 보고되고 뒤의 둘은 사유가 있다. 변환은 원본 파일을 바꾸지 않는다 | 예 | Markdown, HTML 수행. HWPX는 공개 시험 파일 49개, XLSX와 PDF는 직접 만든 작은 파일로만 확인. DOCX는 지원하지 않는다 |
| S2 | **전수 검토**. 문서마다 종류, 날짜, 주제, 상태를 판정하고 문제를 올린다 | 변환된 모든 문서가 여섯 상태 중 하나를 가진다. 상충, 낡음, 중복 문제에는 원문 그대로의 인용이 있다. 끊긴 참조와 빈 곳은 "없다"는 주장이므로, 참조하는 쪽의 인용과 어디를 찾아봤는지를 적는다. 근거를 대지 못한 판정은 "판단 불가"다 | 예 | 수행. 판정 에이전트 일부가 더 작은 모델로 돌았다 |
| S3 | **대조 검증**. 판정을 쓴 쪽과 다른 에이전트가 원문과 대조한다 | 문제 전부와 지식 전부가 일치, 불일치, 판단 불가 중 하나를 받는다. 검증자는 새 맥락에서 시작하고, 문제의 설명과 근거 인용과 원문만 받는다. 판정자의 추론 과정과 이전 검증 결과는 받지 않는다. 실행 기록에 검증자의 식별자가 남아 판정자나 이전 검증자와 다름을 확인할 수 있다 | 예 | 수행. 첫 검토에서는 표본만 검증했고 두 번째 대조를 같은 에이전트가 이어서 했다. 뒤에 바로잡았다 |
| S4 | **지식 구성**. 주제마다 자료 안내를 만든다 | 주제마다 정본이 있거나, 정본이 없다는 사실과 이유가 적혀 있다. 함께 볼 문서, 유효하지 않은 문서, 알려진 어긋남을 적는다. 모든 문단에 인용이 있고 인용문 검사가 실패 0건이다 | 예 | 수행. 25개 주제 중 22개에 정본이 정해졌다 |
| S5 | **현황판**. 상태와 변화를 한 화면에서 본다 | 문서 상태, 주제별 지식, 문제 목록, 이력이 나온다. 주제에서 지식 본문, 근거, 원문의 해당 줄까지 화면 안에서 이동한다. 네트워크 없이 열린다 | 예 | 수행 |
| S6 | **수정 계획**. 문제마다 무엇이 맞는지 확인하고 고칠 방법을 정한다 | 맞는 쪽을 문서 밖의 근거(코드, 설정, 스크립트)나 정본 문서로 확인하고 그 위치를 적는다. 문제를 여섯 가지로 나눈다: 수정, 사람 결정 필요, 문서가 아닌 쪽이 틀림, 문제 아님, 고치지 않음(당시의 기록), 범위 제외. 사람이 계획을 승인하기 전에는 원본을 고치지 않는다 | 텍스트 원본과 대조할 근거가 있는 묶음만 | 그런 묶음 하나에서 수행 |
| S7 | **재판정**. 고친 뒤 실제로 해소됐는지 확인한다 | 수정에 참여하지 않은 에이전트가 문제별로 해소 여부, 같은 문서에 같은 서술이 남았는지, 새 어긋남이 생겼는지를 판정한다. 바뀐 문서를 인용한 지식이 갱신되고 다시 검증된다 | S6과 같음 | 수행 |
| S8 | **이력**. 검토할 때마다 현행 문서 수와 남은 문제 수가 쌓인다 | 이전 검토와의 차이가 현황판에 나온다. 남은 문제 수가 다음 식과 맞는다: 직전 남은 수 − 해결 − 이번에 틀린 판정·고치지 않음·범위 제외로 바꾼 수 + 새로 생겨 남은 수 | 예 | 수행(세 줄). 집계가 한 번 틀려 바로잡았다 |
| S9 | **에이전트의 사용**. 에이전트가 자료 안내를 읽고 일하며, 지식이 없거나 틀리면 신고한다 | 에이전트에게 주는 도구에 지식과 원본을 쓰는 기능이 없다. 신고가 저장되고, 다음 검토의 판정 단계가 신고 목록을 입력으로 받았음이 실행 기록에 남는다 | 아니오 | 신고를 받고 그것으로 틀린 지식을 찾는 것은 사전 실험에서 수행. 전수 검토의 입력으로 쓰는 것과, 지식이 일의 정확도를 올리는지는 미확인 |

초기 범위의 중심은 S2, S3, S5, S6, S7이다. S1, S4, S8은 이들을 받치는 단계이고 S9는 10절의 실험 결과를 보고 넣는다.

판정 대상은 문서다. 코드와 설정은 S6에서 맞는 쪽을 확인하는 근거로 읽지만, 코드 주석 같은 것을 판정 대상으로 삼지는 않는다.

## 7. 실험에서 얻은 규칙

각 규칙은 그것이 없을 때 생긴 오류에서 나왔다. **고정**은 설정으로 끌 수 없게 하는 것이고, **기본값**은 근거가 한두 건이거나 대상 하나에서만 본 것이라 다음 대상에서 다시 확인할 것이다.

| 규칙 | 근거 | 강도 |
| - | - | - |
| 판정과 지식에는 원문 그대로의 인용이 있어야 한다. 없으면 판단 불가다 | 인용 없는 요약은 검증할 방법이 없다 | 고정 |
| 쓴 쪽과 검증하는 쪽은 다른 주체다. 사람의 승인은 대조 검증을 통과한 것만 받는다 | 인용문 검사와 사람 승인을 모두 통과한 지식 9건 중 5건이 틀렸다 | 고정 |
| 원본을 고치는 일은 사람이 계획을 승인한 뒤에 한다 | 원본은 사용자의 것이다 | 고정 |
| 수정은 재판정을 거쳐야 해결로 기록된다 | 수정 56건 중 12건이 한 번에 해소되지 않았고, 수정이 새 문제 6건을 만들었다 | 고정 |
| 항목의 식별자를 바꾸지 않는다 | 수정 중에 문제가 지워지자 순번으로 이은 대조 결과 3건이 다른 항목에 붙었다 | 고정 |
| 문제는 표본이 아니라 전부 대조 검증한다 | 처음 검증한 표본은 25건 중 5건이 틀렸는데, 표본 밖 46건은 17건이 틀렸다 | 기본값 |
| 상충이나 낡음으로 올리기 전에 두 문서가 같은 대상, 같은 시점을 말하는지 확인한다 | 문제 판정에서 가장 흔한 오류였다(불일치 17건 중 7건) | 기본값 |
| 원문이 말한 범위와 시점을 넘겨 쓰지 않는다 | 지식에서 가장 흔한 오류였다 | 기본값 |
| 문서를 고칠 때 같은 문서에서 같은 내용을 말하는 곳을 모두 찾는다 | 재판정에서 되돌아온 12건의 대부분이 이 경우였다 | 기본값 |
| 지식의 기본 유형은 자료 안내다. 규칙은 원문에 규칙으로 적혀 있는 것을 그대로 가리키는 경우로 한정한다 | 대상 하나에서, 여러 원문을 종합해 쓴 규칙 4건 중 3건이 두 번 고쳐도 어긋났다 | 기본값 |
| 문서와 다른 근거가 어긋날 때 문서가 틀렸다고 가정하지 않는다 | 소유자가 "설계가 맞고 코드가 틀렸다"고 확인한 사례가 1건 있었다 | 기본값 |
| 사라진 인용을 비슷한 문장으로 자동 대체하지 않는다 | 자동으로 고른 12건 중 7건이 엉뚱한 줄이었다 | 기본값 |

자료 안내도 여러 문서를 함께 보고 쓰는 것이라 첫 작성에서는 25건 중 20건이 어긋났다. 자료 안내가 규칙과 다른 점은 틀리지 않는다는 것이 아니라, 대조 검증과 수정을 두 번 안에 통과했다는 것이다.

## 8. 제품이 맡을 일

실험에서는 사람과 진행 세션이 절차 문서를 보고 손으로 이어 붙였다. 제품은 이 부분을 맡는다. 판정과 수정안 작성 자체는 LLM이 한다.

| 제품이 맡는 것 | 실험에서 드러난 필요 |
| - | - |
| 단계의 순서와 에이전트 격리 | 두 번째 대조를 같은 에이전트가 이어서 한 일이 있었다. 진행 세션이 대응표를 폴더 밖에 숨겨 격리해야 했다 |
| 검토 상태의 저장과 식별자 관리 | 순번이 밀려 대조 결과가 어긋난 일이 한 번 있었고, 같은 원인의 사고를 한 번 더 미리 막았다 |
| 인용의 위치 추적 | 문서 41개를 고치자 지식 25건 중 20건을 손봐야 했다. 줄 번호만 밀린 것은 자동으로 갱신하고, 문장이 바뀐 것은 다시 쓸 대상으로 표시한다. 해결된 문제의 옛 인용은 따로 보존한다 |
| 집계와 검산 | 남은 문제 수가 한 번 틀렸다 |
| 현황판 생성 | |
| 비용과 시간의 기록 | 한 회차의 토큰에 계획 단계가 포함됐는지 확인하지 못한 값이 있다 |
| 사람 승인 지점 | 수정 계획, 사람 결정이 필요한 문제 |

**범용 에이전트에 절차 문서만 주는 것과의 차이.** 실험이 바로 그 방식이었고 결과도 그것으로 얻었다. 제품이 더하는 것은 위 표의 일, 곧 절차의 강제와 상태 관리다. 판정의 품질 자체를 올린다는 근거는 없다. 이 차이가 따로 만들 만한 값인지는 두 번째 대상에서 "절차 문서만 준 경우에 사람이 개입한 횟수와 사고 수"를 세어 판단한다.

## 9. 비목표

**하지 않는다**

- 채팅 서비스, 답 생성 기능, 자체 에이전트 엔진
- 사람의 승인 없는 원본 수정
- 실시간 공동 편집
- 서버로 운영하는 그래프 DB

**초기 범위에서 하지 않고 나중에 검토한다**

- 여러 원문을 종합한 규칙이나 요약 지식의 생성. 10절의 실험 결과에 따라 다시 본다
- 대조할 근거가 없거나 원본을 텍스트로 고칠 수 없는 묶음의 수정 고리
- 팀 기능: 다중 사용자 인증, 서버 측 권한, 동기화
- Knowledge Canvas, 문서 산출물 생성, 프로젝트 관리 모듈
- OCR, 음성 인식
- 코드 주석처럼 문서가 아닌 것을 판정 대상으로 삼는 검토

## 10. 처음의 가설을 어떻게 다루는가

"검증된 지식이 있으면 에이전트가 더 정확하게 일한다"는 기각된 것이 아니라 맞는 대상에서 시험해 보지 못한 것이다. 에이전트가 직접 읽기 어려운 자료(HWPX, XLSX, PDF, 회의록)에서 [문서 실험](../experiments/doc/README.md)의 절차로 확인한다. 자료는 소유자가 준비한다.

- 지지되면 S9를 초기 범위에 넣고, 에이전트용 검색과 MCP, 지식 유형의 확대를 검토한다. 그때 이 문서의 6절, 7절, 9절을 개정한다.
- 지지되지 않으면 S9는 신고 수집에 머물고, 제품은 문서 점검 도구로 남는다.

## 11. 재는 것

실험의 값을 첫 기준선으로 둔다. **목표 수치는 아직 정하지 않았다.** 대상 하나의 값으로 합격선을 정하면 그 대상에 맞춘 숫자가 되기 때문이다. 두 번째 대상에서 한 번 더 잰 뒤에 정한다.

| 지표 | 계산 | 실험의 값 |
| - | - | - |
| 첫 판정의 오류율 | 대조 검증에서 불일치로 나온 문제의 비율 | 84건 중 22건(26%). 소유자가 확정한 1건을 더하면 23건 |
| 검증을 통과한 오판 | 대조 검증을 통과한 뒤 문제가 아니거나 고칠 필요가 없는 것으로 드러난 비율 | 61건 중 5건 |
| 첫 지식의 오류율 | 대조 검증에서 불일치로 나온 지식의 비율 | 25건 중 20건 |
| 검증끼리의 일치 | 같은 문제를 다른 검증자가 다시 봤을 때 같은 판정의 비율 | 8건 중 7건 |
| 수정의 재작업률 | 재판정에서 한 번에 해소되지 않은 비율 | 56건 중 12건(21%) |
| 남은 문제의 추이 | 검토마다의 남은 문제 수 | 61 → 49 → 2 |
| 지식 유지 비용 | 문서 수정 한 회차에 손본 지식의 비율 | 문서 14개 수정에 25건 중 13건, 문서 41개 수정에 25건 중 20건 |
| 문서당 비용 | 전 과정의 토큰을 문서 수로 나눈 값 | 약 3만 6천~3만 9천 토큰 |
| 놓친 문제의 비율 | 사람이 미리 알고 있는 문제 중 검토가 찾아낸 비율 | 재지 않았다 |
| 다시 돌렸을 때의 일치 | 같은 묶음을 두 번 검토했을 때 겹치는 문제의 비율 | 재지 않았다 |
| 사람의 시간 | 승인과 결정에 쓴 시간 | 문서 검토에서는 재지 않았다 |

## 13. LLM 사용 방침

개발과 실험은 외부 LLM API로 한다. LLM 호출은 포트 뒤에 둔다. 변환, 인용문 검사, 집계, 현황판 생성은 LLM 없이 동작한다.

외부로 보내도 되는 자료만 쓴다. 가려야 할 내용은 변환 전에 원본에서 지운다. 인증서와 키 파일은 변환 대상에서 뺀다. 폐쇄망 동작과 내부 모델에서의 품질은 따로 검증하며, 외부 모델로 얻은 11절의 값은 내부 모델에 그대로 적용되지 않는다.

## 14. 가정과 미확인 사항

| 항목 | 현재 상태 | 정하는 곳 |
| - | - | - |
| 다른 문서 묶음에서도 같은 결과가 나오는가 | 대상 하나에서만 수행 | 두 번째 대상에서의 검토 |
| 놓친 문제의 비율과 재실행 일치 | 재지 않았다 | 두 번째 대상의 검토 계획. 알려진 문제를 미리 적어 두거나 심어 놓고 발견율을 잰다 |
| 계속할지의 기준 | 없다. 사람의 시간을 포함한 문제 1건당 비용이 얼마 이하여야 계속하는지 정해야 한다 | 두 번째 대상의 검토 계획 |
| 대조할 코드가 없는 묶음의 수정 계획 | 미확인. 대부분 "사람 결정 필요"가 되어 승인 부담이 커질 수 있다 | 오피스 문서 실험 |
| HWPX, XLSX, PDF 원본의 수정 방식 | 변환이 한 방향이라 수정을 원본에 되써 넣을 방법이 없다 | 오피스 문서 실험 뒤 |
| 수정의 주체와 반영 경로 | 실험에서는 대상 저장소의 에이전트가 그 저장소의 규칙대로 브랜치에 커밋했고 병합은 소유자가 지시했다. gotgan이 직접 쓰는지 수정안만 내는지 미정 | ADR-001 개정 |
| HWPX, XLSX, PDF의 변환 품질 | 공개 시험 파일과 작은 생성 파일로만 확인 | 오피스 문서 실험 |
| 문서 수가 수천 건일 때의 비용과 시간 | 미확인. 314건에 약 1,130만~1,230만 토큰이 들었고, 주제별 판정은 문서를 묶어 읽으므로 문서 수보다 가파르게 늘 수 있다 | 규모 실험 |
| 사용자가 gotgan 밖에서 문서를 고쳤을 때 다시 판정할 범위 | 실험에서는 바뀐 파일과 그것을 인용한 지식만 다시 봤다 | Vault 규격 |
| 행위자의 식별 단위 | 에이전트 실행 하나인지, 모델인지, 사람인지 미정. "다른 주체"를 강제하려면 필요하다 | Vault 규격 |
| 검토 상태의 저장 형식 | 실험에서는 JSON 한 파일 | ADR-001 개정, Vault 규격 |
| 현황판에 원문 전체가 들어가는 것 | 314건에 약 10.9MB. 민감 자료와 팀 공유, 규모에서의 취급 미정 | Vault 규격 |
| 원본이 Git 저장소가 아닐 때의 판본 식별과 수정 되돌리기 | 미정 | ADR-001 개정 |
| 문서 상태 여섯 가지와 문제 종류 다섯 가지가 고정인가 | 대상 하나에서 쓴 분류 | 두 번째 대상에서의 검토 |
| 내부 모델에서의 판정 품질 | 미확인 | 내부 모델 전환 시 |
| 1차 사용자가 소유자 본인인가, 개발 인원, 팀으로 넓히는 시점 | 미확인 | 소유자 확인 |
