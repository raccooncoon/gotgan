# 제품 정의

- 상태: 초안
- 날짜: 2026-11-27

무엇을, 누구를 위해, 어디까지 만드는지 정한다. 이후의 평가 설계, ADR, Vault 규격은 이 문서를 전제로 한다.

## 1. 한 줄 정의

gotgan은 프로젝트 자료를 수집해 **근거를 확인할 수 있는 지식**으로 관리하고, 사람과 에이전트가 같은 지식을 쓰게 하는 파일 기반 지식 창고다.

## 2. 사용자

| 구분 | 대상 | 이 문서에서의 취급 |
| - | - | - |
| 1차 | 개인 1인. 자기 프로젝트 자료를 직접 관리한다 | 초기 범위의 유일한 구현 대상 |
| 2차 | 소규모 팀. 공유 Vault를 함께 쓴다 | 구현은 미루되 설계가 막지 않도록 한다 |

### "팀을 고려한다"의 의미

개인용으로 만들면서 팀 전환 비용을 낮추기 위해, 지금 지킬 것과 미룰 것을 나눈다.

| 지금 지킨다 | 미룬다 |
| - | - |
| 모든 변경에 행위자(사람 또는 에이전트)를 기록한다 | 다중 사용자 인증 |
| 원본과 지식의 메타데이터에 접근 등급 필드를 둔다 | 서버 측 권한 강제 |
| 지식에 신뢰 등급을 둔다. 개인의 자기 승인은 `self-approved`로 구분한다 | 팀 승인 워크플로우 |
| 식별자는 Vault를 합쳐도 충돌하지 않게 만든다 | Vault 간 동기화와 충돌 해결 |
| 저장소, 검색 인덱스, LLM은 포트 뒤에 둔다 | PostgreSQL, MinIO, OpenSearch 구현 |
| 유스케이스는 CLI에 묶지 않는다. 서버에서 같은 유스케이스를 호출할 수 있어야 한다 | HTTP 서버, 웹 화면 |
| Vault마다 식별자와 소유자를 둔다 | 감사 조회, 백업 운영 |

왼쪽 항목은 나중에 추가하면 기존 데이터를 고쳐야 하는 것들이다. 오른쪽 항목은 포트 구현이나 기능 추가로 붙일 수 있는 것들이다.

## 3. 풀려는 문제

아래는 기획 논의에서 추정한 것이며 실제 사용으로 확인되지 않았다.

1. 프로젝트 자료가 여러 형식과 위치에 흩어져 있어, 현재 유효한 내용이 무엇인지 찾기 어렵다.
2. LLM이 답을 주어도 그 근거를 원본에서 확인하기 어렵다.
3. 같은 질문을 할 때마다 원본을 처음부터 다시 탐색한다.
4. 문서끼리 내용이 상충하거나 개정되어도 알아차리지 못한다.

## 4. 핵심 시나리오

| ID | 시나리오 | 완료 조건 | 단계 |
| - | - | - | - |
| S1 | **자료 수집**. 폴더를 지정하면 문서를 수집한다 | 원본이 변경 없이 보존된다. 중복은 한 번만 저장된다. 처리하지 못한 파일은 사유와 함께 목록에 나온다 | 1 |
| S2 | **근거 있는 질의**. 질문하면 답과 근거 위치를 받는다 | 각 근거가 원본의 버전과 위치를 가리킨다. 그 위치의 원문을 바로 열어 확인할 수 있다 | 1 |
| S3 | **지식 승격**. 반복해서 쓰일 내용을 지식으로 제안하고 검증·승인해 반영한다 | 인용문이 원본에 실재하는지 자동 검사를 통과한다. 승인 기록과 신뢰 등급이 남는다. 반영을 되돌릴 수 있다 | 2 |
| S4 | **원본 개정 대응**. 원본의 새 버전을 수집한다 | 이전 버전을 근거로 한 지식이 "재검증 필요"로 표시된다 | 3 |
| S5 | **에이전트 사용**. 외부 에이전트가 CLI나 MCP로 검색하고 변경안을 제출한다 | 에이전트는 정본을 직접 고칠 수 없다. 제출한 변경안은 사람의 것과 같은 절차를 거친다 | 3 |

## 5. 비목표

초기 범위(1~3단계)에서 만들지 않는다.

- 채팅 서비스
- 자체 에이전트 엔진. 기존 에이전트를 CLI와 MCP로 연결한다
- Knowledge Canvas, 관계 그래프 화면, 블록 편집기
- 문서 산출물 생성(Word, Excel, PowerPoint, HWP)
- SI 프로젝트 관리 모듈과 외부 시스템(결함, 일정, 테스트) 연동
- 실시간 공동 편집
- 그래프 DB
- 녹음 파일의 STT와 화자 분리. 회의록은 텍스트로 받는다

4단계에서 다시 검토할 후보이며, 그때 이 문서를 개정한다.

## 6. LLM 사용 방침

개발과 실험은 **외부 LLM API**로 진행한다. 이는 "외부 API 없이 동작한다"는 원칙과 시점이 다를 뿐 충돌하지 않도록 다음과 같이 정한다.

- LLM과 임베딩 호출은 포트 뒤에 둔다. 공급자를 바꿔도 유스케이스 코드는 바뀌지 않는다.
- LLM 없이 동작해야 하는 기능을 구분한다: 수집, 파싱, 키워드 검색, 무결성 검사(`verify`), 인용문 실재 검사.
- 폐쇄망 동작과 내부 모델 성능은 4단계 전에 따로 검증한다. 외부 모델로 얻은 실험 결과는 내부 모델에 그대로 적용되지 않으므로, 같은 평가셋을 내부 모델로 다시 실행한다.
- 외부 API로 보내는 자료는 반출이 허용된 것만 쓴다. 실제 프로젝트 문서를 쓸 경우 반출 가능 여부를 먼저 확인하고, 필요하면 익명화한다.

## 7. 성공 기준

수치는 평가 설계에서 정한다. 여기서는 무엇을 볼지만 정한다.

- S1: 처리 실패가 숨겨지지 않는다. 수집한 원본의 해시가 보존된다.
- S2: 답의 근거가 실제로 그 내용을 담고 있다. 근거에서 원문 위치까지 도달하는 데 걸리는 시간이 짧다.
- S3: 검증된 지식을 쓴 조건(C)이 인덱스만 쓴 조건(B)보다 정확도나 재사용성에서 낫다. 낫지 않으면 큐레이션 범위를 축소한다.
- 제품 전체: 1차 사용자가 자기 프로젝트 하나의 자료를 넣고 일상 업무 질문에 실제로 쓴다.

## 8. 대표 자료 요건

평가에 쓸 자료는 프로젝트 소유자가 준비한다. 다음을 만족해야 실험이 의미를 가진다.

- 형식: 회의록(텍스트), PDF, HWPX, XLSX를 각각 포함한다.
- 같은 주제의 개정본이 있다. S4와 "현재 유효한 내용 식별"을 평가하기 위해서다.
- 서로 상충하는 내용이 있는 문서 쌍이 있다.
- 여러 문서를 종합해야 답할 수 있는 주제가 있다.
- 외부 API로 보낼 수 있다.
- 코드 저장소에 올리지 않는다. 별도 위치에 두고 해시 목록만 기록한다.
