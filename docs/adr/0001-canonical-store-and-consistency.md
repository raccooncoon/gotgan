# ADR-001: 정본 저장소와 일관성 모델

- 상태: 제안
- 날짜: 2026-11-27

## 배경

Vault의 파일이 정본이고 DB·검색 인덱스·그래프는 파생 데이터라는 원칙을 세웠다. 그런데 변경안 반영, 도메인 이벤트 발행, 동시 수정 감지는 트랜잭션을 필요로 한다. 파일 쓰기와 DB 커밋은 원자적으로 묶을 수 없으므로, 무엇을 유일한 진실로 삼고 나머지를 어떻게 복구할지 먼저 정해야 한다. 이 결정은 Vault 규격, Aggregate 설계, 이벤트 처리 방식의 전제다.

요구 조건:

1. Vault 디렉터리만 복사하면 지식, 근거, 이력이 함께 이동한다.
2. 반영 도중 프로세스가 죽어도 정본이 중간 상태로 남지 않는다.
3. DB와 인덱스를 지워도 Vault에서 전부 재구축할 수 있다.
4. 승인된 변경만 정본에 들어갔는지 사후에 검증할 수 있다.
5. 외부 통신 없는 환경에서 동작한다.

## 검토한 선택지

| 선택지 | 내용 | 평가 |
| - | - | - |
| A. DB 정본 | DB가 정본이고 파일은 내보내기 결과 | 조건 1, 3 위배. 파일 기반 작업 환경이라는 제품 방향과 어긋난다. |
| B. 파일 + DB 이중 쓰기 | 파일을 쓰고 DB에 Outbox로 이벤트 기록 | 두 쓰기가 원자적이지 않다. 불일치 복구 규칙이 복잡해진다. |
| C. Git 커밋 원장 | Git 커밋이 유일한 트랜잭션 로그, DB는 프로젝션 | 조건 1~5 충족. Git 이력의 특성(삭제 어려움, 대용량 부적합)을 보완해야 한다. |
| D. 자체 append-only 로그 | 자체 형식의 변경 로그를 Vault에 기록 | 조건은 충족하나 diff, 무결성, 도구 호환을 직접 구현해야 한다. |

## 결정

**C를 채택한다.** Vault는 Git 저장소이고, 정본의 상태는 `HEAD` 커밋이다.

### 1. 반영은 커밋 하나다

변경안 반영(`apply`)은 다음을 한 커밋에 담는다.

- `knowledge/` 아래 지식 파일 변경
- `proposals/` 아래 변경안의 상태 변경
- `history/` 아래 검증·승인 기록

커밋 메시지 트레일러에 검증에 필요한 값을 남긴다.

```
Proposal-Id: prop-2026-0042
Proposal-Hash: sha256:...
Base-Revision: sha256:...
Reviewed-By: reviewer-agent-1
Approved-By: human:hong
```

작업 트리는 진실이 아니다. 시작 시 커밋되지 않은 변경이 있으면 반영 도중 중단된 것으로 보고 `HEAD`로 되돌린다. 단, 사용자가 직접 편집한 파일은 5항의 규칙을 따른다.

### 2. 동시 수정은 대상 버전 비교로 막는다

변경안은 작성 시점의 대상 파일 해시(`Base-Revision`)를 기록한다. 반영 시점에 현재 해시와 다르면 반영하지 않고 재검증 상태로 돌린다. Vault당 쓰기는 한 번에 하나만 수행한다(개인형은 파일 잠금, 서버형은 반영 서비스가 직렬화).

### 3. 이벤트는 커밋에서 파생한다

프로젝터가 마지막으로 처리한 커밋 이후의 커밋을 읽어 DB와 인덱스를 갱신하고 도메인 이벤트(`KnowledgePublished` 등)를 만든다. 처리 위치는 DB에 체크포인트로 저장하고, 커밋 SHA를 멱등 키로 쓴다. 별도의 Outbox 테이블은 두지 않는다.

### 4. 원본 바이너리는 Git 밖에 둔다

첫 검증 대상인 소스코드처럼 원본이 이미 Git 저장소에 있으면 복사하지 않고 저장소 식별자와 커밋으로 가리킨다. 그 외의 원본 파일은 내용 해시로 주소를 매겨 `sources/blobs/` 아래에 저장하고 Git에서 제외한다. Git은 원본의 메타데이터(해시, 버전, 접근 등급, 추출 품질)만 추적한다. Vault 이동 시에는 Git 저장소와 blob 디렉터리를 함께 옮긴다. `verify`가 메타데이터의 해시와 실제 blob의 일치를 검사한다.

### 5. 직접 편집은 감지해서 변경안으로 돌린다

유효한 트레일러가 없는 커밋이나 커밋되지 않은 `knowledge/` 변경은 미승인 변경이다. 개인형에서는 `verify`가 이를 감지해 변경안으로 전환하도록 안내한다. 서버형에서는 반영 서비스만 정본 브랜치에 쓸 수 있고 그 외의 푸시는 거부한다. 배포 등급별 차이는 ADR-002에서 정한다.

### 6. 복구

- DB나 인덱스 손상: 삭제 후 첫 커밋부터 다시 프로젝션한다.
- 반영 중 중단: 커밋 전이면 작업 트리를 `HEAD`로 되돌리고, 커밋 후면 프로젝터가 이어서 처리한다.
- 잘못된 반영: 되돌리는 변경안을 새로 만들어 같은 절차로 반영한다. 이력을 다시 쓰지 않는다.

## 결과

얻는 것:

- 파일과 DB 사이의 원자성 문제가 사라진다. DB는 언제든 버릴 수 있다.
- 변경 비교, 이력, 무결성 검사를 Git이 제공한다.
- Java에서는 JGit을 쓰면 외부 git 실행 파일 없이 동작한다.

치르는 비용:

- 조회는 프로젝션이 따라올 때까지 약간 늦을 수 있다. 반영 직후 조회가 필요한 유스케이스는 프로젝션 완료를 기다려야 한다.
- 지식 파일 수와 이력이 커지면 Git 성능을 확인해야 한다. 한계 규모는 측정하지 않았다.
- Vault 규격이 Git에 묶인다.

## 남은 문제

- **파기**: 원본 blob은 삭제할 수 있지만, 지식 파일에 인용된 민감 문구는 Git 이력에 남는다. 이력 재작성을 허용할지, 인용문을 암호화해 키를 폐기할지 정해야 한다.
- **Vault 간 동기화**: 개인·팀·기업 Vault 사이의 공유를 Git 원격으로 할지 내보내기 묶음으로 할지는 별도 ADR에서 다룬다.
- **변경안 저장 위치**: 변경안을 정본 브랜치의 `proposals/`에 둘지 별도 브랜치에 둘지. 현재 안은 이동성을 위해 정본 브랜치에 패치 파일로 둔다.
- **JGit 검증**: 대용량 저장소 성능과 파일 잠금 동작은 1단계에서 확인한다.
