# 문서 폴더 전수 검토와 지식 구성

문서 폴더 하나를 전부 읽고, 무엇이 현행이고 무엇이 낡았는지, 어디가 서로 어긋나는지를 판정한 뒤, 주제별 지식으로 구성하고 현황판으로 보여 준다. [문서 실험](README.md)의 비교 실험보다 먼저 한다. 여기서 만든 지식을 나중에 비교 실험의 조건 C에 쓴다.

## 1. 지켜야 할 것

- 원본과 대상 저장소는 읽기만 한다. 산출물은 실험 폴더(`lab/`)에만 쓰고 어디에도 푸시하지 않는다.
- `review.json`과 현황판에는 문서 제목과 경로가 들어간다. 이 저장소(gotgan)에 올리지 않는다.
- 인증서, 키, 접속 정보가 든 파일은 `originals/`로 복사하지 않고, 어떤 산출물에도 그 값을 넣지 않는다.
- **판정에는 근거를 붙인다.** "낡음", "상충", "중복" 판정은 근거가 되는 위치와 인용문이 있어야 한다. 근거를 대지 못하면 "판단 불가"로 둔다. 사전 실험에서 근거 없이 요약한 지식의 절반이 틀렸다.
- 작업 규모가 크다. 시작 전에 소유자에게 예상 규모(문서 수, 띄울 에이전트 수)를 알린다.

## 2. 절차

1. **변환.** `convert.py`로 `originals/` → `text/`. `manifest.json`의 실패와 부분 추출을 기록한다. `text/`를 커밋한다.
2. **문서 카드.** 문서마다 카드 하나를 만든다(3절 `docs`). 폴더 단위로 나눠 여러 에이전트가 병렬로 읽는다. 이 단계에서는 문서 하나만 보고 알 수 있는 것만 적는다: 종류, 제목, 날짜, 다루는 내용 한 줄, 다른 문서를 가리키는 언급.
3. **주제 묶기.** 카드를 모아 주제를 정한다. 주제는 10~30개를 목표로 한다. 문서 하나가 여러 주제에 속할 수 있다.
4. **주제별 판정.** 주제마다 그 주제의 문서들을 함께 읽고 판정한다.
   - 정본: 지금 기준이 되는 문서. 없으면 비운다.
   - 문서별 상태(4절).
   - 문제(5절): 상충, 낡음, 중복, 끊긴 참조, 빈 곳.
5. **지식 구성.** 주제마다 OKF 지식 파일 하나를 `knowledge/자료-안내/<주제>.md`로 쓴다. 내용은 "이 주제는 어디를 보면 되는가"다: 정본과 그 근거, 함께 볼 문서, 더 이상 유효하지 않은 문서와 그 이유, 알려진 어긋남. 원문 내용을 길게 복사하지 않는다. 형식과 규칙은 사전 실험의 큐레이터 스킬을 따르고, 근거의 경로는 `text/` 아래 파일이다.
6. **인용문 검사.** `verify_sources.py <lab/knowledge> <lab>` 실패 0건.
7. **대조 검증.** 판정과 지식을 쓴 에이전트와 다른 새 에이전트가 확인한다. 대상은 지식 파일 전부와, 문제(issues) 중 심각도 높음 전부와 나머지에서 고른 표본이다. 결과를 각 항목의 `verified`에 적는다. 불일치로 나온 판정은 고치거나 "판단 불가"로 내린다.
8. **집계와 현황판.** `review.json`을 쓰고 `python board/build_board.py lab/report/review.json lab/report/board.html`로 현황판을 만든다.
9. **소유자에게 보여 준다.** `board.html`을 열어 보여 주고, 판정이 틀린 곳을 알려 달라고 한다. 소유자가 고친 판정은 `review.json`에 `verified: "소유자 확인"`으로 반영한다.

현황판은 외부 자원 없이 열리는 HTML 한 파일이다. 주제를 누르면 문제와 문서 목록이 그 주제로 좁혀지고, 문제마다 근거 인용을 펼쳐 볼 수 있다. 문제 목록에는 대조 검증에서 "불일치"로 나온 것도 표시와 함께 남기되, 손봐야 할 것의 수에서는 뺀다.

## 3. review.json 형식

```json
{
  "meta": {
    "corpus": "docs",
    "commit": "<대상 저장소 커밋>",
    "generated_at": "2026-11-27T09:00:00Z",
    "convert": {"성공": 0, "부분 추출": 0, "실패": 0}
  },
  "docs": [
    {
      "id": "d001",
      "path": "<폴더>/<파일>",
      "folder": "<최상위 하위 폴더. 루트면 '(루트)'>",
      "kind": "설계 | 계획 | 리뷰 | 계약 | 운영 | 보고 | 가이드 | 기록 | 자료 | 기타",
      "title": "문서 제목",
      "date": "2026-10-12",
      "lines": 120,
      "topics": ["t01"],
      "state": "현행 | 대체됨 | 상충 | 중복 | 기록 | 판단 불가",
      "superseded_by": "d045",
      "note": "상태를 그렇게 본 이유 한 줄",
      "convert": "성공 | 부분 추출 | 실패"
    }
  ],
  "topics": [
    {
      "id": "t01",
      "name": "주제 이름",
      "summary": "이 주제가 무엇인지 한두 문장",
      "canonical": "d012",
      "docs": ["d001", "d012"],
      "knowledge": "knowledge/자료-안내/<주제>.md"
    }
  ],
  "issues": [
    {
      "id": "i001",
      "kind": "상충 | 낡음 | 중복 | 끊긴 참조 | 빈 곳",
      "severity": "높음 | 중간 | 낮음",
      "topic": "t01",
      "docs": ["d001", "d020"],
      "what": "무엇이 어떻게 어긋나는지 한두 문장",
      "evidence": [{"doc": "d001", "loc": "L120", "quote": "짧은 인용"}],
      "verified": "일치 | 불일치 | 판단 불가 | 미검증 | 소유자 확인"
    }
  ],
  "knowledge": [
    {"path": "knowledge/자료-안내/<주제>.md", "topic": "t01", "sources": 5, "crosscheck": "일치 | 불일치 | 판단 불가"}
  ],
  "history": [
    {"commit": "<커밋>", "date": "2026-11-27", "docs": 315, "current": 0, "issues_open": 0}
  ]
}
```

`date`는 파일 이름이나 본문에서 확인되는 날짜다. 없으면 비운다. `history`는 검토할 때마다 한 줄씩 늘린다. 나중에 같은 폴더를 다시 검토하면 변화가 보인다.

## 4. 문서 상태

| 상태 | 뜻 | 필요한 것 |
| - | - | - |
| 현행 | 지금 유효하다. 더 새로운 문서가 대신하지 않는다 | 없음 |
| 대체됨 | 더 새로운 문서가 같은 내용을 대신한다 | `superseded_by`와 근거 |
| 상충 | 다른 현행 문서와 어긋나는 내용이 있고 어느 쪽이 맞는지 문서만으로 알 수 없다 | 해당 문제(issue) |
| 중복 | 다른 문서와 내용이 사실상 같다 | 해당 문제 |
| 기록 | 특정 시점의 기록(회의, 리뷰, 보고)이라 현행 여부를 따지지 않는다 | 없음 |
| 판단 불가 | 근거가 부족하다 | `note`에 이유 |

날짜가 더 늦다는 것만으로 "대체됨"으로 판정하지 않는다. 뒤의 문서가 앞의 것을 대신한다고 밝혔거나, 같은 항목을 다르게 정했을 때만 그렇게 판정한다.

## 5. 문제의 종류

| 종류 | 뜻 |
| - | - |
| 상충 | 두 문서가 같은 것을 다르게 말한다 |
| 낡음 | 문서가 폐지되거나 바뀐 것을 여전히 현행처럼 적고 있다 |
| 중복 | 같은 내용이 여러 곳에 있어 한쪽만 고쳐질 위험이 있다 |
| 끊긴 참조 | 가리키는 문서나 절이 없다 |
| 빈 곳 | 여러 문서가 전제로 삼는데 어디에도 적혀 있지 않다 |

심각도는 그 어긋남을 믿고 일했을 때의 피해로 정한다. 잘못된 배포나 데이터 손상으로 이어질 수 있으면 높음, 헛수고로 끝나면 중간, 표기 차이 정도면 낮음.
