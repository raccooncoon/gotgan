# 문서 폴더 전수 검토와 지식 구성

문서 폴더 하나를 전부 읽고, 무엇이 현행이고 무엇이 낡았는지, 어디가 서로 어긋나는지를 판정한 뒤, 주제별 지식으로 구성하고 현황판으로 보여 준다. [문서 실험](README.md)의 비교 실험보다 먼저 한다. 여기서 만든 지식을 나중에 비교 실험의 조건 C에 쓴다.

## 1. 지켜야 할 것

- 원본과 대상 저장소는 읽기만 한다. 산출물은 실험 폴더(`lab/`)에만 쓰고 어디에도 푸시하지 않는다.
- `review.json`과 현황판에는 문서 제목과 경로가 들어간다. 이 저장소(gotgan)에 올리지 않는다.
- 인증서, 키, 접속 정보가 든 파일은 `originals/`로 복사하지 않고, 어떤 산출물에도 그 값을 넣지 않는다.
- **판정에는 근거를 붙인다.** "낡음", "상충", "중복" 판정은 근거가 되는 위치와 인용문이 있어야 한다. 근거를 대지 못하면 "판단 불가"로 둔다. 사전 실험에서 근거 없이 요약한 지식의 절반이 틀렸다.
- 작업 규모가 크다. 시작 전에 소유자에게 예상 규모(문서 수, 띄울 에이전트 수)를 알린다.
- 스크립트는 PyYAML이 필요하다. 실험 폴더 옆에 가상환경 하나를 만들어 모든 에이전트가 같이 쓴다.
- 지식과 문제를 쓸 때 원문이 말한 범위와 시점을 넘지 않는다. 원문이 특정 대상이나 특정 시점에 대해 한 말을 "정본이다", "더 이상 유효하지 않다"로 세게 옮기지 않는다. 같은 문서 안의 정정으로 이미 해소된 어긋남은 문제로 올리지 않는다.

## 2. 절차

1. **변환.** `convert.py`로 `originals/` → `text/`. `manifest.json`의 실패와 부분 추출을 기록한다. `text/`를 커밋한다.
2. **문서 카드.** 문서마다 카드 하나를 만든다(3절 `docs`). 폴더 단위로 나눠 여러 에이전트가 병렬로 읽는다. 이 단계에서는 문서 하나만 보고 알 수 있는 것만 적는다: 종류, 제목, 날짜, 다루는 내용 한 줄, 다른 문서를 가리키는 언급.
3. **주제 묶기.** 카드를 모아 주제를 정한다. 주제는 10~30개를 목표로 한다. 문서 하나가 여러 주제에 속할 수 있다.
4. **주제별 판정.** 주제마다 그 주제의 문서들을 함께 읽고 판정한다. 상충이나 낡음으로 올리기 전에 두 문서가 같은 대상, 같은 시점을 말하는지, 뒤에서 이미 정정되지 않았는지 먼저 확인한다.
   - 정본: 지금 기준이 되는 문서. 없으면 비운다.
   - 문서별 상태(4절).
   - 문제(5절): 상충, 낡음, 중복, 끊긴 참조, 빈 곳.
5. **지식 구성.** 주제마다 OKF 지식 파일 하나를 `knowledge/자료-안내/<주제>.md`로 쓴다. 내용은 "이 주제는 어디를 보면 되는가"다: 정본과 그 근거, 함께 볼 문서, 더 이상 유효하지 않은 문서와 그 이유, 알려진 어긋남. 원문 내용을 길게 복사하지 않는다. 형식과 규칙은 사전 실험의 큐레이터 스킬을 따르고, 근거의 경로는 `text/` 아래 파일이다.
6. **인용문 검사.** `verify_sources.py <lab/knowledge> <lab>` 실패 0건.
7. **대조 검증.** 판정과 지식을 쓴 에이전트와 다른 새 에이전트가 확인한다. 대상은 문제(issues) 전부와 지식 파일 전부다. 문제를 먼저 검증하고, 불일치로 나온 문제에 기댄 지식 문단을 고친 뒤에 지식을 검증한다. 다시 검증할 때도 이전 대조를 한 에이전트를 이어 쓰지 않는다. 결과를 각 항목의 `verified`에 적는다. 불일치로 나온 판정은 고치거나 "판단 불가"로 내린다.
8. **집계와 현황판.** `lab/report/review.json`을 쓰고 `python board/build_board.py lab lab/report/board.html`로 현황판을 만든다. 경고가 0건이 될 때까지 `review.json`과 지식 파일을 고친다.
9. **소유자에게 보여 준다.** `board.html`을 열어 보여 주고, 판정이 틀린 곳을 알려 달라고 한다. 소유자가 고친 판정은 `review.json`에 `verified: "소유자 확인"`으로 반영한다.

현황판은 외부 자원 없이 열리는 HTML 한 파일이다. `text/`의 원문과 `knowledge/`의 지식 파일이 함께 들어가므로, 화면 안에서 주제 → 지식 본문 → 근거 → 원문의 그 줄까지 따라갈 수 있다. 주제를 누르면 그 주제의 지식과 근거가 나오고, 근거를 누르면 원문이 옆에 열리며 해당 줄이 강조된다. 문제의 근거와 문서 목록의 제목도 같은 방식으로 원문을 연다.

원문의 줄은 인용문으로 찾는다. 그래서 **`evidence`의 `quote`는 `text/` 파일에 있는 글자 그대로여야 한다.** 여러 줄에 걸쳐도 되지만 말을 바꾸거나 줄이면 찾지 못하고 경고가 난다. 줄 번호를 알면 `line`(과 `line_end`)을 직접 적어도 된다. 문제 목록에는 대조 검증에서 "불일치"로 나온 것도 표시와 함께 남기되, 손봐야 할 것의 수에서는 뺀다.

## 3. review.json 형식

```json
{
  "meta": {
    "corpus": "docs",
    "commit": "<대상 저장소 커밋>",
    "generated_at": "2026-11-27T09:00:00Z",
    "convert": {"성공": 0, "부분 추출": 0, "실패": 0}
  },
  "docs": [
    {
      "id": "d001",
      "path": "<폴더>/<파일>",
      "folder": "<최상위 하위 폴더. 루트면 '(루트)'>",
      "kind": "설계 | 계획 | 리뷰 | 계약 | 운영 | 보고 | 가이드 | 기록 | 자료 | 기타",
      "title": "문서 제목",
      "date": "2026-10-12",
      "lines": 120,
      "topics": ["t01"],
      "state": "현행 | 대체됨 | 상충 | 중복 | 기록 | 판단 불가",
      "superseded_by": "d045",
      "note": "상태를 그렇게 본 이유 한 줄",
      "convert": "성공 | 부분 추출 | 실패"
    }
  ],
  "topics": [
    {
      "id": "t01",
      "name": "주제 이름",
      "summary": "이 주제가 무엇인지 한두 문장",
      "canonical": "d012",
      "docs": ["d001", "d012"],
      "knowledge": "knowledge/자료-안내/<주제>.md"
    }
  ],
  "issues": [
    {
      "id": "i001",
      "kind": "상충 | 낡음 | 중복 | 끊긴 참조 | 빈 곳",
      "severity": "높음 | 중간 | 낮음",
      "topic": "t01",
      "docs": ["d001", "d020"],
      "what": "무엇이 어떻게 어긋나는지 한두 문장",
      "evidence": [{"doc": "d001", "quote": "원문에 있는 글자 그대로의 인용", "line": 120, "line_end": 121}],
      "verified": "일치 | 불일치 | 판단 불가 | 미검증 | 소유자 확인",
      "status": "열림 | 해결됨",
      "resolution": "해결됐을 때: 무엇을 어떻게 고쳤는지 한 줄"
    }
  ],
  "knowledge": [
    {"path": "knowledge/자료-안내/<주제>.md", "topic": "t01", "sources": 5, "crosscheck": "일치 | 불일치 | 판단 불가"}
  ],
  "history": [
    {"commit": "<커밋>", "date": "2026-11-27", "docs": 315, "current": 0, "issues_open": 0}
  ]
}
```

문서, 주제, 문제의 `id`는 한 번 정하면 바꾸지 않는다. 수정 중에 항목을 지워도 남은 항목의 번호를 당기지 않는다. 대조 검증 결과를 `id`로 짝짓기 때문이다.

`date`는 파일 이름이나 본문에서 확인되는 날짜다. 없으면 비운다. `history`는 검토할 때마다 한 줄씩 늘린다. 나중에 같은 폴더를 다시 검토하면 변화가 보인다.

## 4. 문서 상태

| 상태 | 뜻 | 필요한 것 |
| - | - | - |
| 현행 | 지금 유효하다. 더 새로운 문서가 대신하지 않는다 | 없음 |
| 대체됨 | 더 새로운 문서가 같은 내용을 대신한다 | `superseded_by`와 근거 |
| 상충 | 다른 현행 문서와 어긋나는 내용이 있고 어느 쪽이 맞는지 문서만으로 알 수 없다 | 해당 문제(issue) |
| 중복 | 다른 문서와 내용이 사실상 같다 | 해당 문제 |
| 기록 | 특정 시점의 기록(회의, 리뷰, 보고)이라 현행 여부를 따지지 않는다 | 없음 |
| 판단 불가 | 근거가 부족하다 | `note`에 이유 |

날짜가 더 늦다는 것만으로 "대체됨"으로 판정하지 않는다. **뒤의 문서가 앞의 문서 전체를 대신한다고 밝힌 경우에만** "대체됨"으로 판정하고, 그 선언을 근거로 인용한다. 일부 항목만 바뀌었으면 문서 상태는 "현행"으로 두고 바뀐 항목을 "낡음" 문제로 올린다. 첫 전수 검토에서 판정자가 "대체됨"으로 본 22건 중 16건이 대조 검증에서 되돌려졌다.

## 5. 문제의 종류

| 종류 | 뜻 |
| - | - |
| 상충 | 두 문서가 같은 것을 다르게 말한다 |
| 낡음 | 문서가 폐지되거나 바뀐 것을 여전히 현행처럼 적고 있다 |
| 중복 | 같은 내용이 여러 곳에 있어 한쪽만 고쳐질 위험이 있다 |
| 끊긴 참조 | 가리키는 문서나 절이 없다 |
| 빈 곳 | 여러 문서가 전제로 삼는데 어디에도 적혀 있지 않다 |

심각도는 그 어긋남을 믿고 일했을 때의 피해로 정한다. 잘못된 배포나 데이터 손상으로 이어질 수 있으면 높음, 헛수고로 끝나면 중간, 표기 차이 정도면 낮음.

## 6. 문제를 고친 뒤의 부분 재검토

문서를 고친 뒤 폴더 전체를 다시 검토하지 않고, 고친 부분만 확인해 현황판을 갱신한다.

1. 고친 문서가 반영된 커밋으로 고정 복제본을 옮기고, 바뀐 파일만 다시 변환해 `text/`를 커밋한다.
2. 고친 문제마다, 수정에 참여하지 않은 새 에이전트가 새 원문을 보고 판정한다: 어긋남이 실제로 없어졌는가, 고치면서 다른 문서와 새 어긋남이 생기지 않았는가. 없어졌으면 `status: "해결됨"`과 `resolution`을 적는다. 새 어긋남은 새 `id`의 문제로 올리고 대조 검증한다.
3. 바뀐 문서를 근거로 삼은 지식 파일의 인용문과 줄 범위를 새 원문에 맞춰 고친다. 내용이 달라진 문단은 다시 쓰고 대조 검증한다. `verify_sources.py` 실패 0건.
4. 바뀐 문서의 상태(상충 등)를 다시 판정한다.
5. `meta.commit`을 새 커밋으로 바꾸고 `history`에 한 줄을 추가한다. `current`는 현행 문서 수, `issues_open`은 불일치와 해결됨을 뺀 문제 수다.
6. 현황판을 다시 만든다.

| 인용문 검사 | 지식의 인용문 356건과 판정 근거 인용문 모두 실패 0건 |
| 현황판 | 빌드 경고 0건, 파일 크기 약 10.9MB |

**대조 검증이 없었다면 대부분 틀린 채로 나갔다.**

| 대상 | 1차 대조 검증 | 처리 뒤 |
| - | - | - |
| 지식 25건 | 일치 5, 불일치 20 | 일치 24. 남은 1건은 어긋난 문단을 지움 |
| 문제 표본 25건 | 일치 20, 불일치 5 | 불일치 5건은 표시를 남기고 손볼 수에서 뺌 |
| 심각도 높음 5건 | 4건이 과대 판정 | 중간이나 낮음으로 내림 |
| 문서 상태 "대체됨" | 22건 | 6건. 대체 선언이 없는데 대체됨으로 본 16건을 되돌림 |

오류의 모양은 사전 실험과 같았다. 원문이 특정 범위나 시점에 대해 한 말을 "정본이다", "대체됐다", "더 이상 유효하지 않다"로 세게 옮겼다. 인용문은 전부 원문에 있었다.

**결과를 읽을 때 주의할 점.**

- 문제 84건 중 대조 검증을 거친 것은 38건(일치 33, 불일치 5)이고 46건은 검증하지 않았다. 표본에서 5건 중 1건꼴로 틀렸으므로, 검증하지 않은 46건에도 비슷한 비율의 오류가 있을 수 있다.
- 2차 대조 검증은 1차와 같은 에이전트가 이어서 했다. 수정한 쪽과는 다른 에이전트지만, 1차 때의 판단을 기억하고 있어 완전히 새 눈은 아니다.
- 판정 에이전트 일부가 더 작은 모델로 실행됐다.
- 소유자의 확인은 아직 받지 않았다.

**도구와 절차에서 고친 점.** "대체됨"의 기준을 전체 대체 선언이 있을 때로 좁혔다. 항목의 `id`를 바꾸지 않도록 했다. 원문의 범위와 시점을 넘겨 쓰지 않도록 했다. 가상환경을 하나만 쓰도록 했다.
