# 사전 실험: 코드 없이 큐레이션 가설 확인

제품 코드를 쓰기 전에 "검증된 지식을 만들어 두면 에이전트가 저장소의 규칙을 더 잘 지킨다"는 가설을 확인한다. 배경은 [참고 자료 분석](../../docs/references.md) 5절에 있다.

이 폴더의 스킬과 스크립트는 일회용 실험 도구이며 제품 코드가 아니다.

## 1. 지켜야 할 것

- **대상 저장소를 바꾸지 않는다.** 파일 수정, 커밋, 브랜치나 워크트리 생성, 빌드, 실행을 하지 않는다. 읽기만 한다.
- 실험 산출물은 대상 저장소 **밖의** 실험 폴더(이하 `lab/`)에만 쓴다.
- `lab/`은 어디에도 푸시하지 않는다. 대상 저장소의 내용, 기관명, 내부 주소, 비밀 값을 이 저장소(gotgan)에 올리지 않는다.
- 과제는 "답변 또는 작업 계획 작성"으로 한정한다. 에이전트가 실제로 코드를 고치게 하지 않는다.
- 사람의 승인 없이 지식을 정본(`lab/`의 `main` 브랜치)에 넣지 않는다.

## 2. 실험 폴더 구조

`lab/`은 Git 저장소다. `main` 브랜치가 정본이다.

```
lab/
├─ knowledge/        # OKF v0.3 형식의 지식 파일. index.md에 okf_version 기록
├─ flags/            # 신고. F-<과제ID>-<회차>-<순번>.md 형식
├─ tasks/            # 평가 과제와 채점 기준. T-01.md 형식
├─ runs/<회차>/      # 과제별 에이전트 출력
├─ scores/<회차>.json
└─ report/metrics.json
```

## 3. 조건과 회차

| 회차 | 에이전트가 쓸 수 있는 것 |
| - | - |
| `r0` 현행 | 대상 저장소 그대로(기존 지침 파일과 문서 포함) |
| `r1` 지식 추가 | 위와 같음 + `lab/knowledge/` |

두 회차 모두 과제마다 **맥락이 없는 새 에이전트**가 수행한다. 실험을 진행하는 세션의 기억이나 대화 내용을 과제 에이전트에게 넘기지 않는다. 두 회차 모두 신고 스킬을 준다.

## 4. 절차

1. **준비**: `lab/`을 만들고 `git init` 한다. 대상 저장소가 작업 중에 바뀌지 않도록, 저장소 밖에 읽기용 복제본을 만들어 한 커밋에 고정하고 그 커밋을 `lab/TARGET`에 기록한다. 과제, 큐레이터, 검사 모두 이 복제본을 본다. 스크립트는 PyYAML이 필요하므로 `lab/` 옆에 가상환경을 만들어 설치한다.
2. **과제 작성과 동결**: 과제 12개를 쓴다(5절). `dev` 6개와 `holdout` 6개로 나눈다. 커밋하고 이후 고치지 않는다.
3. **r0 실행**: 과제마다 새 에이전트에게 과제 문장만 준다. 과제 에이전트는 파일을 쓸 수 없는 읽기 전용으로 돌린다. 출력을 `runs/r0/`에 저장하고, 답변 끝에 적힌 신고를 진행하는 쪽이 `flags/`로 옮긴다. 옮길 때 신고의 `at`(실제 시각), `round`, `by`를 진행하는 쪽이 채우고, 문자열 값은 따옴표로 감싸 머리말이 YAML로 읽히는지 확인한다.
4. **r0 채점**: 채점 전용 새 에이전트 하나가 그 회차의 모든 과제를 채점 기준으로 항목별로 매긴다. 판정 이유도 함께 받아 `scores/r0-reasons.md`에 둔다. 결과는 `scores/r0.json`에 저장한다.
5. **큐레이션**: 큐레이터 스킬로 변경안을 만든다. 입력은 **`dev` 과제에서 나온 신고**와 대상 저장소다. `holdout` 과제의 문장, 채점 기준, 출력, 신고는 큐레이터에게 보여 주지 않는다. 이를 위해 `dev` 신고만 복사한 별도 폴더를 만들어 큐레이터에게 주고, 결과를 `lab/`의 `proposal/1` 브랜치로 옮겨 커밋한다.
6. **자동 검사**: `scripts/verify_sources.py`가 모든 인용문이 기록된 커밋의 그 위치에 있는지 검사한다. 실패가 있으면 큐레이터가 고친다.
7. **사람 승인**: 여기서 멈추고 소유자에게 변경안을 보여 준다. 소유자가 승인한 지식만 `main`에 병합하고, 그 파일에 사람의 확인 기록을 남긴다.
8. **r1 실행과 채점**: 3~4와 같은 방법으로 같은 과제를 다시 돌린다. 이번에는 `lab/knowledge/`의 위치를 알려 준다.
9. **집계**: `scripts/metrics.py`로 `report/metrics.json`을 만든다.

스크립트 사용법:

```
python verify_sources.py <lab/knowledge> <대상 저장소 복제본>
python metrics.py <lab>
```

## 5. 과제 형식

대상 저장소에서 실제로 있었거나 있을 법한 작업 요청으로 쓴다. 규칙을 과제 문장에 드러내지 않는다. 규칙을 알아야 올바르게 답할 수 있어야 한다.

```markdown
---
id: T-01
split: dev            # dev 또는 holdout
area: backend
checks:
  - id: c1
    text: 변경 뒤 전체 테스트를 돌려야 한다고 계획에 적었다
  - id: c2
    text: 공용 DB의 데이터를 넓게 바꾸는 테스트를 제안하지 않았다
---

(에이전트에게 그대로 주는 과제 문장)
```

채점 항목은 예 또는 아니오로 판정할 수 있게 쓴다. 과제마다 2~4개.

`dev`와 `holdout`은 다루는 규칙이 서로 겹치지 않게 나눈다. `holdout`에서도 개선이 보이면 지식이 그 과제에 맞춰진 것이 아니라 일반적으로 쓸모 있다는 뜻이다.

## 6. 채점 파일 형식

```json
[
  {"task": "T-01", "check": "c1", "pass": true},
  {"task": "T-01", "check": "c2", "pass": false}
]
```

통과하지 못한 항목 하나가 규칙 위반 1회다.

## 7. 재는 것

| 지표 | 계산 |
| - | - |
| 규칙 위반 | 회차별 통과하지 못한 채점 항목 수. `dev`와 `holdout`을 따로 센다 |
| 신고 | 회차별 접수 수, 지식에 반영돼 닫힌 수 |
| 신고 재발 | 이전 회차의 신고와 같은 주제로 다시 들어온 신고. 이전 신고가 닫혔는지와 상관없이 `repeat_of`를 적는다. 닫힌 신고의 재발은 지식이 문제를 풀지 못했다는 뜻이고, 열린 신고의 재발은 처리가 밀려 있다는 뜻이다 |
| 지식 상태 | 유형별·영역별 수, 확인 등급(사람 검토, 기계 확인, 미확인) |
| 근거 검사 | 검사한 인용문 수, 실패 수, 검사할 수 없는 근거 수 |
| 사람의 검토 시간 | 소유자가 승인에 쓴 시간(분). 소유자가 알려 준 값을 `report/review_minutes.txt`에 적는다 |

## 8. 한계

- 과제가 12개이고 회차당 한 번씩만 돌린다. 결과는 방향을 보는 용도이며 통계적 결론이 아니다.
- 채점을 에이전트가 한다. 소유자가 일부를 직접 확인해 채점이 믿을 만한지 본다.
- 과제가 계획 작성이라, 실제 코드 수정에서의 규칙 준수와 다를 수 있다.
- `dev` 과제는 큐레이터가 그 신고를 보고 지식을 만들므로 개선되는 것이 당연하다. 가설의 근거는 `holdout` 결과다.
- 인용문 검사는 대상 저장소 안의 파일에만 적용된다. 사람의 진술이나 관찰에서 온 근거는 검사할 수 없다.

## 9. 성공과 중단 기준

실험 전에 정한다.

- **가설 지지**: `holdout`의 규칙 위반이 `r0`보다 `r1`에서 줄고, 근거 검사 실패가 0건이다.
- **가설 약함**: `dev`만 줄고 `holdout`은 그대로다. 지식이 과제에 맞춰졌을 뿐이라는 뜻이다.
- **가설 기각**: 둘 다 줄지 않는다. 큐레이션 설계를 다시 본다.
- 소유자의 검토 시간이 지식 한 건당 너무 길면, 위반이 줄어도 비용 문제로 기록한다.

## 10. 진행 기록

### 1차 과제 세트, r0 (2026-11-27)

| 항목 | 값 |
| - | - |
| 채점 항목 | 29개 (dev 16, holdout 13) |
| 규칙 위반 | 2회 (dev 1, holdout 1) |
| 신고 | 28건 (없음 20, 틀림 7, 낡음 1) |
| 큐레이터 변경안 | 지식 9건 (규칙 4, 자료 안내 5) |
| 근거 검사 | 인용문 24건, 실패 0건 |
| 근거를 찾지 못한 신고 | dev 신고 14건 중 5건 |

**천장 효과.** 대상 저장소의 기존 지침 파일이 이미 강해서 r0에서 29개 중 27개를 통과했다. holdout 위반이 1회뿐이라 r1에서 줄어드는 것을 보일 여지가 거의 없다. 9절의 기준으로는 이 과제 세트에서 가설을 판정할 수 없다.

**없다는 주장은 지식이 되지 못했다.** 신고의 대부분(28건 중 20건)이 "문서가 없다"는 유형이다. 없다는 사실은 파일 인용으로 증명할 수 없어서, 큐레이터 규칙상 지식으로 만들지 못했다. 가장 값이 클 것으로 보이는 지식(어디에도 적히지 않은 규칙과 함정)이 바로 이 유형이다.

**도구 수정.** 진행 중 발견된 문제를 반영했다: 신고 파일 이름에 회차 추가, 머리말 값의 따옴표 안내, 깨진 머리말을 만나도 집계가 멈추지 않고 알리도록 변경, 각주 없는 문단을 검사 실패로 처리, 큐레이터 격리 방법과 읽기용 복제본 고정을 절차에 명시.

### 1차 과제 세트, r1 (2026-11-27)

소유자가 변경안 9건을 모두 승인했고, 같은 과제를 지식과 함께 다시 돌렸다.

| 항목 | r0 | r1 |
| - | - | - |
| 규칙 위반, dev (항목 16개) | 1 | 0 |
| 규칙 위반, holdout (항목 13개) | 1 | 1 |
| 신고 접수 | 28 | 23 |
| 지식을 명시적으로 인용한 답변 (12개 중) | 해당 없음 | 5 |

**판정: 가설 약함, 다만 판정력이 거의 없다.** dev만 줄고 holdout은 그대로다. holdout에 남은 위반 1회는 지식 9건이 다루지 않은 규칙이었다. r0부터 위반이 2회뿐이라 이 세트로는 어느 쪽으로도 결론을 낼 수 없다.

**승인된 지식 9건 중 2건에 오류가 있었다.** 둘 다 인용문 검사와 사람 승인을 통과했고, r1의 과제 에이전트가 "틀림"으로 신고해서 드러났다.

- 요약이 원문을 바꿨다: 원문은 원인을 두 가지로 나눠 적었는데 지식은 전부 한 가지 원인으로 적었다.
- 인용한 원문 자체가 틀렸다: 근거로 삼은 주석의 내용이 실제 설정과 달랐다.

여기서 알게 된 것:

- 인용문 검사는 "그 문장이 그 자리에 있다"만 보증한다. 지식이 원문을 정확히 옮겼는지, 원문이 사실인지는 보증하지 않는다.
- 사람 승인도 두 오류를 걸러내지 못했다. 9건을 한꺼번에 검토할 때 근거 원문과 대조까지 하기는 어렵다.
- 신고가 오류를 찾아냈다. 지식을 쓰는 에이전트가 틀린 지식을 신고하는 고리는 동작했다.

**기타 관찰.** 에이전트가 신고의 시각을 지어낸 경우가 있었다. 채점자가 "애매하면 실패"로 판정해, 규칙을 실제로 지켰지만 말로 밝히지 않은 답을 위반으로 셌다. 신고 머리말의 따옴표 문제가 r1에서도 재발했다.

### 대조 검증 소급 시험 (2026-11-27)

1차 세트에서 승인된 지식 9건에 대조 검증을 돌렸다. 검증 에이전트에게는 어느 것이 오류인지 알려 주지 않았다.

| 항목 | 값 |
| - | - |
| 판정 | 일치 4건, 불일치 5건, 판단 불가 0건 |
| 이미 알려진 오류 2건 | 둘 다 불일치로 잡음 |
| 새로 찾은 불일치 3건 | 진행하는 쪽이 근거 줄을 열어 확인한 결과 셋 다 실제 오류 |
| 잘못 잡은 것 | 0건 |
| 소요 시간 | 검증 에이전트 1회 약 4분 |

**인용문 검사와 사람 승인을 통과한 지식 9건 중 5건이 원문과 어긋났다.** 오류의 모양은 두 가지로 모인다.

- 원문이 나눠 적은 경우를 하나로 합쳤다.
- 특정 대상에 대한 서술을 일반 규칙으로 넓혔다.

주의할 점:

- 새로 찾은 3건이 실제 오류인지는 실험을 진행한 세션이 판정했다. 독립된 사람의 확인은 아니다.
- 알려진 오류 하나는 파일 단위로는 잡았지만, 인용한 주석이 실제 설정과 다르다는 점 자체는 "결론에 영향 없음"으로 넘겼다. 파일이 불일치가 된 직접 이유는 다른 문제였다.
- 표본이 9건이다. 잘못 잡은 것이 0건이라는 결과를 일반화할 수 없다.

**근거 검사의 빈틈.** 각주 검사가 문단 단위라, 각주 있는 문장 뒤에 같은 문단으로 붙은 각주 없는 문장은 걸리지 않는다.

**계획에 주는 의미.** 큐레이터가 쓴 지식은 인용문이 실재해도 절반 넘게 원문을 왜곡할 수 있다. 원문과의 대조 검증은 선택 사항이 아니라 승인 전의 필수 단계여야 한다. 사람 승인은 대조 검증이 걸러낸 뒤의 것만 보게 해야 한다.

## 11. 2차 과제 세트

1차 세트의 결과를 본 뒤에 추가한 것이므로, 사전에 정한 설계에서 벗어난 변경이다(2026-11-27 소유자 결정). 1차 세트의 과제와 결과는 고치지 않고 그대로 두며, 2차 세트는 따로 집계한다. 여기 적지 않은 것은 1~9절을 그대로 따른다.

### 겨냥하는 것

대상 저장소의 주 지침 파일에 **없는** 규칙만 다룬다. 두 종류가 있다.

| 종류 | 설명 | 큐레이터가 알 수 있는 경로 |
| - | - | - |
| 흩어진 규칙 | 주 지침 파일에는 없지만 다른 곳(다른 문서, 작업 기록, 코드 주석, 저장소 밖 메모)에는 적혀 있다 | 원천 자료를 읽어서 |
| 적히지 않은 함정 | 어디에도 적혀 있지 않다 | 신고를 받고 관찰하거나 소유자에게 물어서 |

### 과제

- ID는 `U-01`~`U-12`, 회차 이름은 `s2r0`과 `s2r1`이다.
- `holdout` 6개는 **흩어진 규칙**만 겨냥한다. 큐레이터가 과제를 보지 않고도 원천 자료에서 찾아낼 수 있어야 holdout이 의미를 가진다.
- `dev` 6개는 두 종류를 섞는다. 적히지 않은 함정은 여기에만 넣는다.
- 과제를 쓰는 쪽은 규칙을 이미 알고 있으므로, 과제 문장과 채점 기준에 규칙이나 그 위치를 드러내지 않도록 주의한다.

### 천장 확인

과제를 동결하고 `s2r0`을 돌린 뒤 채점한다. 위반이 채점 항목의 3분의 1에 못 미치면 여기서 멈추고 보고한다. 그 경우 새 에이전트가 이미 이 규칙들을 알고 있거나 스스로 찾아낸다는 뜻이며, 그것 자체가 결과다. 과제를 고쳐서 위반을 늘리지 않는다.

### 큐레이션

- 입력: `dev` 과제의 신고, 대상 저장소, 저장소 밖 메모 등 원천 자료 전체. `holdout` 과제의 문장, 채점 기준, 출력, 신고는 보여 주지 않는다.
- `proposal/2` 브랜치에 커밋한다.
- 근거의 종류를 다음과 같이 쓴다.

| `x-gotgan-kind` | 쓰는 경우 | 자동 검사 |
| - | - | - |
| `file` | 대상 저장소 안의 파일 | 한다 |
| `observation` | 저장소 밖 파일의 내용, 읽기 전용 명령의 결과. `x-gotgan-note`에 무엇을 언제 어떻게 확인했는지 적는다 | 못 한다 |
| `human` | 소유자가 직접 말한 내용. `x-gotgan-note`에 누가 언제 말했는지 적는다 | 못 한다 |

- 적히지 않은 함정처럼 근거가 없는 주제는 큐레이터가 지어내지 않는다. 변경안 보고에 "소유자 확인 필요" 목록으로 올리고, 소유자가 답한 내용만 `human` 근거로 지식에 넣는다.
- 저장소 밖 메모가 대상 저장소의 문서와 어긋나면 덮어쓰지 않고 두 내용을 나란히 보고한다.

### 대조 검증 (승인 전)

1차 세트에서 인용문 검사와 사람 승인을 모두 통과한 오류가 2건 나왔다. 그래서 승인 전에 단계를 하나 더 둔다.

큐레이터와 다른 새 에이전트가 지식 파일마다 다음을 확인하고, 문단별로 "일치", "불일치", "판단 불가"와 이유를 적는다. 지식을 고치지 않고 보고만 한다.

1. 문단의 내용이 인용한 원문과 같은가. 원문보다 넓게 말하거나, 좁게 말하거나, 여러 경우를 하나로 합치지 않았는가.
2. 인용한 원문이 주석이나 설명 문서라면, 그것이 가리키는 실제 코드나 설정과 맞는가.

"불일치"가 나온 지식은 큐레이터가 고치거나 변경안에서 뺀다. 결과는 `report/crosscheck-<제안 번호>.md`에 남긴다.

**소급 시험.** 이 단계가 쓸모 있는지 보려고, 2차 세트 전에 1차 세트의 승인된 지식 9건에 먼저 돌린다. 이미 알려진 오류 2건을 "불일치"로 잡는지, 나머지 7건 중 잘못 "불일치"로 판정하는 것이 몇 건인지 기록한다. 검증 에이전트에게는 어느 것이 오류인지 알려 주지 않는다.

### 승인

소유자는 지식의 내용 자체가 맞는지 확인하고 승인한다. `observation`과 `human` 근거는 자동 검사가 없으므로 이 확인이 유일한 검증이다. 승인에 쓴 시간(분)을 `report/review_minutes_s2.txt`에 적는다.

### 판정

- **가설 지지**: `holdout`의 위반이 `s2r0`보다 `s2r1`에서 줄었다. 흩어진 규칙을 모아 두는 것이 새 에이전트에게 도움이 된다는 뜻이다.
- **가설 약함**: `dev`만 줄었다. 신고받은 것만 채워졌고 원천 자료에서 스스로 찾아 모으는 데는 실패했다는 뜻이다.
- **기각**: 둘 다 줄지 않았다.

### 한계

- `human` 근거의 지식은 "소유자가 그렇게 말했다"는 것만 보증한다. 집계에서 파일 근거만 가진 지식과 구분해 센다.
- 과제를 쓰는 쪽이 규칙을 알고 있어, 그 규칙이 드러나도록 과제가 쓰였을 수 있다.
- 1차 세트와 같은 한계(과제 수, 에이전트 채점, 계획 작성 과제)가 그대로 적용된다.
